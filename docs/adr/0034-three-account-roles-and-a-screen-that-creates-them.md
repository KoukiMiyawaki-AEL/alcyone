# 0034. アカウントの権限を3段階にし、作成する画面を持つ

## Status

Accepted（[ADR 0032](./0032-inviting-by-email-and-bootstrapping-the-admin.md)の
2段階（member / admin）を3段階に広げる）

## Context

[ADR 0032](./0032-inviting-by-email-and-bootstrapping-the-admin.md)は
「最初のアカウントが管理者になる」で管理者の不在を解消したが、そこから先が無かった。

- **アカウントを作る手段が画面に無い。** 増やす方法はサインアップだけで、
  誰がどの権限で入ってくるかを運用側が決められない。メール基盤が無いので
  招待も送れない（[ADR 0013](./0013-better-auth.md)）。
- **管理者と、その上が区別できない。** 管理者は他の管理者を任命でき、降格もできる。
  つまり**管理者は全員が同格**で、最初に作られたアカウントを含めて誰でも誰でも降ろせる。
  「このインスタンスの持ち主」という立場が表現できていなかった。

## Decision

### `owner` / `admin` / `member` の3段階

`USER_ROLES` を**弱い順の配列**として定義し、順序そのものを規則にする。

| 役割 | できること |
|---|---|
| `member` | 自分のプロジェクトと、招待されたプロジェクト |
| `admin` | すべてのプロジェクトの参加者を変更。アカウントの追加。member ↔ admin の変更 |
| `owner` | 管理者のすべてに加えて、**オーナーと管理者の任命・解任** |

規則は2つだけ:

1. **管理者は `owner` に手を出せない。** 任命もできないし、オーナーを降格もできない。
   これが無いと、管理者が自分を任命した相手を降ろせてしまう。
2. **最後のオーナーは降ろせない。** 権限を渡せるのはオーナーだけなので、
   ひとりもいない状態からは戻れない。

どちらもWHEREに入れて1文にする。2文に分けると、最後の2人が同時に互いを降格できる。

**`owner` はインスタンスのオーナーであって、プロジェクトのオーナーではない。**
後者は `projects.ownerId` で、別のスコープの別の概念である。同じ語が2つを指さないよう、
画面ではプロジェクト側を「プロジェクトの作成者」と呼ぶ。

**最初に作られたアカウントは `admin` ではなく `owner` になる。**

### 値域はトリガーで守る（CHECKではなく）

このリポジトリの規約は「値域の制約はCHECKでDB側にも置く」だが、**ここでは破る**。

SQLiteは既存テーブルに制約を追加できないので、CHECKを足すには `user` を作り直すしかない。
そして `session.userId` と `account.userId` は `user` を **ON DELETE CASCADE** で参照している
——古いテーブルを落とした時点で、**全セッションと全資格情報が黙って消える**
（[ADR 0011](./0011-expand-contract-migrations.md)がこのテーブルについて記録した危険そのもの）。

`BEFORE INSERT` と `BEFORE UPDATE OF role` のトリガーで `RAISE(ABORT)` する。
保証は同じで、行に触らない。

### アカウントを作る画面

`/admin` に、名前・メールアドレス・初期パスワード・権限のフォームを置く。

**Better Auth のサインアップ経路を通す。** 直接INSERTしないのは、
検証するコードと同じコードでハッシュさせるため。

**返ってきたセッションを転送しない。** サインアップのレスポンスは新しいアカウントの
セッションを持っている。ヘッダをそのまま返すと、**管理者が今作った人に入れ替わる**。

**権限は行が生まれる前に検査する。** 作ってから拒むと、既定の権限のまま
中途半端なアカウントが残る。

**初期パスワードは管理者が決めて本人に渡す。** これは弱点である——
他人が決めたパスワードは、変更されるまで他人も知っている。
正しい直し方はメール送信であって、フォームの工夫ではない。ここに書いて残す。

## Consequences

### 得たもの

- 「このインスタンスの持ち主」が表現でき、管理者に降ろされない。
- 運用側がアカウントを、権限まで含めて用意できる。サインアップの順番に依存しない。
- 役割の値域がDB側でも守られる（テーブルを作り直さずに）。

### 残っている穴

- **初期パスワードを管理者が知っている。** 強制的な変更も、有効期限も無い。
- **招待メールが送れない。** アカウント作成は「作って手渡す」しかない。
- **アカウントを消す画面が無い。** 退会は本人だけができる
  （[ADR 0015](./0015-soft-delete-items-hard-delete-accounts.md)）。
- **権限の変更に監査ログが無い。** 誰がいつ誰を任命したかはどこにも残らない。
- **オーナーが1人だけとは限らない。** 複数許すことにしたので、
  「持ち主」は人ではなく役割として扱う必要がある。
