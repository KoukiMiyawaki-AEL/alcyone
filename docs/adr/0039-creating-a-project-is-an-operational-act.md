# 0039. プロジェクトを作るのは運用の行為とする（作成権限と、作成が生む権限）

## Status

Accepted（[ADR 0036](./0036-what-each-role-is-for.md)が決めた3つの役割に、
唯一その外にあった「作成」を接続する）

## Context

`POST /api/projects` にロールの検査が無かった。**サインインしていれば誰でも作れ、
件数の上限も無い。** そして作った人は `projects.ownerId` になり、
そのプロジェクトの管理権を得る。

[ADR 0036](./0036-what-each-role-is-for.md)は「**ロールは入口ではない**——
参加には必ず誰かが行を作る必要があり、その行が誰がいつを残す」と決めた。
ところが**作成だけがこの原則の外にあった**：自分でプロジェクトを作れば、
誰の承認も無く、自分が管理者である場所を持てる。ロールを絞った意味が、
作成という1つの穴から抜けていた。

穴は2つあり、片方だけ塞ぐと歪む。「誰でも作れる」だけを塞ぐと
「作れる人は無制限に管理者になれる」構造が残り、「作ると管理者になる」だけを
塞ぐと「作ったのに何も設定できない」という誰も望まない状態になる。

## Decision

**プロジェクトを作るのは運用の行為であり、`admin` 以上が行う。**

「どのプロジェクトが存在するか」は組織の決めごとであって、作業の一部ではない。
`owner` だけに絞る案は、オーナー1人が全プロジェクトの作成を担うことになるので採らない。

### 参加条件は付かない

[ADR 0036](./0036-what-each-role-is-for.md)は管理者の**管理権限**に
「そのプロジェクトに参加していること」を条件として付けた。作成には付けない——
**作る時点で参加すべきプロジェクトが存在しない**。同じロールでも問いが違う。

### リポジトリが拒む

`projects.create` が、管理者未満には行を返さない文を返す
（`roles.set` / `directory.list` と同じ形）。ハンドラ側の検査は、
書き忘れが型エラーにもテスト失敗にもならない——このリポジトリが繰り返し踏んだ形である。

絞り込む行が無いので、`where` ではなく「何も選ばない文」になる。

### 拒否は 404

`POST /api/users` と同じ。**ここでの理由は隠蔽ではない**——
作ろうとしているものはまだ存在しないので、隠すものが無い。
それでも「拒否は404」を例外なく保つ方が価値がある：クライアントの `mutate()` に
「403も見る」分岐が増えない。**作法が理由であって、機密が理由ではない**と書き分ける。

### 件数の上限は設けない

権限は「誰が」、上限は「どれだけ」で、別の恐れに答える仕組みである。
作れるのが管理者以上になった時点で、無制限は脅威ではない。

D1が読み取り行数で課金し、ダッシュボードの集計が到達できるプロジェクト数に比例することは
実在の懸念だが、**それはページングの問題**である（[ADR 0033](./0033-project-as-context-not-a-sidebar-item.md)に記録済み）。
混ぜると、上限に当たった人が「権限が無いのか、いっぱいなのか」を判別できなくなる。

### 作成者の管理権は残り、降格でも失わない

`projects.ownerId` はそのまま。**降格された管理者は、自分が作ったプロジェクトを
管理し続ける。** 「作れる資格」と「作ったものへの責任」は別の時点の話で、
後者は資格の取り消しでは消えない。

そうしないと、降格が**そのプロジェクトを一時的に誰も管理できない状態**にする——
参加者の追加も削除もできず、オーナーが気付いて引き取るまで止まる。

### 既存の一般ユーザー所有プロジェクトは、そのまま

自動で移管しない。誰が新しい持ち主かを機械が推測することになり、その推測は必ずどこかで外れる。
**規則が変わる前に作られたものは、変わる前の規則で作られた。**

### 一般ユーザーの画面はボタンを隠す

無効化でも「押すと拒否」でもない。一般ユーザーにとってこれは
**いつかできるようになる操作ではなく、一度もしない操作**なので、
常設の死んだコントロールになる。そして「APIが拒むボタンをUIが出す」形は
[ADR 0031](./0031-project-membership-and-roles.md)が明示的に避けたものである。

空の状態の文面も変える。今の「「プロジェクトを追加」から最初のプロジェクトを作ってください」は、
**その人にできないことを指している**。

## Consequences

### 得たもの

- ロールが作成を含めて一貫した。「参加には必ず誰かが行を作る」に例外が無くなった。
- 誰が管理者であるプロジェクトが増えるかを、運用が決められるようになった。

### 意図した設計（穴ではない）

**一般ユーザーは自分のプロジェクトを持てない。** 作成が運用の行為である以上、
今後作られるプロジェクトの管理権は恒久的に管理者以上に紐づく。一般ユーザーは
参加して働くだけで、自分の担当プロジェクトに1人足すにも管理者を呼ぶ。

譲渡（[ADR 0031](./0031-project-membership-and-roles.md)が穴として記録済み）と
「作成時に持ち主を選ぶ」は、どちらも独立した機能として、必要になったときに独立して判断する。

### メールでの招待の位置づけが変わった

[ADR 0032](./0032-inviting-by-email-and-bootstrapping-the-admin.md)がアドレスでの招待を足したのは、
**名簿が管理者専用で、一般の所有者には選ぶ一覧が無かった**からだった。作成が管理者の行為になった今、
**プロジェクトの作成者は必ず名簿を読める**ので、その理由は消えている。

機能は残す——知っているアドレスを打つ方が短いし、[ADR 0031](./0031-project-membership-and-roles.md)が
書いたとおり「アドレスは招く側が既に知っているもので、渡しても知識を増やさない」。
ただし**必需品ではなく近道になった**ことは記録しておく。

### テストに出た影響

**分離テストの前提が変わった。** 「他人のものが見えない」を確かめるには、
**観測する側が一般ユーザーである必要がある**——管理者は全プロジェクトが見えるので
（[ADR 0036](./0036-what-each-role-is-for.md)）、管理者を観測者にしたテストは
何も証明しない。次の3つを組み直した。

- プロジェクトの一覧：管理者が2つ作り、一般ユーザーを片方に入れて、その1つだけが見えることを見る。
- 検索：検索する側を2人とも一般ユーザーにした。管理者だと両方見つかる。
- 親子・関連の付け替え：操作する側を一般ユーザーにした。管理者は他プロジェクトのタスクに
  正当に到達できるので、404を期待するテストが200で落ちた。

**`signUpAdmin()` を足し、`signUp()` は変えなかった。** 変更は最小になるが、
全テストの主役が管理者になり、**所有スコープのテストが何も証明せずに緑になる**——
このリポジトリで既に2回踏んだ形（最初のアカウントが管理者になる問題、
E2Eアカウントが全員同名だった問題）で、どちらも「気付かないうちに主役が強くなる」だった。

E2Eの管理者アカウントは、**オーナーが `POST /api/users` で作る**
（[ADR 0034](./0034-three-account-roles-and-a-screen-that-creates-them.md)が入れた経路そのもの）。
最初はサインアップしてから昇格させていたが、それだと**ページ自身のアドレスで
`/api/auth/*` を3回**叩く（サインアップ、そして新しいロールを反映させるためのリロード）。
そこは**1分あたり10回**で、`get-session` もその1回に数えられる——長いテストが途中から
「サインインしていない」ように見え始めた。**429は未ログインと見分けが付かない**という、
CLAUDE.mdに既に書いてある罠を、テスト側で踏んだ形である。

そのオーナーのサインインには `Origin` ヘッダが要る（Better Auth が検証する。無いと403。
[ADR 0013](./0013-better-auth.md)に記録済みの罠を、これもテスト側で踏んだ）。

**E2Eのプロジェクト名はスイート全体で一意でなければならなくなった。** 管理者は全プロジェクトが
見え、E2EのDBは1回の実行で共有される。同じ名前を2つのテストが使うと一覧に両方出て、
その名前を指すロケータが全部strict mode違反になる（「Activity」が4つ、「Schedule」が7つ出た）。
**前方一致も同じ**——Playwrightは名前を部分一致で照合するので、`Schedule` は `Schedule 2` にも当たる。
