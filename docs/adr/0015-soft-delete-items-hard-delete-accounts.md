# 0015. 項目は論理削除、アカウントは物理削除にする

## Status

Accepted

## Context

[service-readiness-map](../design/service-readiness-map.md)のD4（削除ポリシー）は、マップを書いた時点から`検討中`のまま残っていた一方通行のドアだった。「**失うのはコードではなくデータ**であり、これは取り返せない」というのが挙げた理由。

認証（[ADR 0013](./0013-better-auth.md)）を入れたことで、この判断を先送りできなくなった。マップが「実ユーザーの1人目の前に」の前提として挙げていた項目のうち、**ユーザーは登録できるのに退会できない**という状態になっていた。加えて `deleteUser` はBetter Authの既定で無効で、有効にすると `projects.ownerId → user.id` のFK（NO ACTION、[ADR 0012](./0012-no-on-delete-cascade.md)）に阻まれる。

## Decision Drivers

- 誤操作からの回復手段があること
- 「データを消して」に対して嘘をつかないこと
- 見えない`where`を増やすことの危険性（D1のオーナー列で学んだばかり）

## Decision

**対象によって答えを変える。**

| 対象 | 方式 | 理由 |
|---|---|---|
| Project / Todo | **論理削除**（`deletedAt`、nullなら生存） | 誤削除からの回復。ゴミ箱の土台 |
| アカウント | **物理削除**（論理削除済みの行も含めて完全に消す） | 「削除しました」が事実であること |

**論理削除はUndoとセットで入れる。** DBに行が残っているだけではユーザーには何の価値も無い。削除時に「元に戻す」アクション付きのtoastを出し、復元エンドポイントを用意した。**これが無ければ `deletedAt` はただの隠し列**であり、論理削除を選ぶ意味がない。

`deletedAt` は nullable なので、マイグレーションは素の `ADD COLUMN` で済む（テーブル再構築なし）。インデックスは複合にした。全ての読み取りが `owner = ? AND deletedAt IS NULL` の形になるので、D1が**スキャンした行数**で課金し1件ずつ処理することを踏まえると、これは整頓ではなく性能上の必要。

**2つ目の不可視フィルタは`src/worker/db/repo.ts`に置く。** オーナーの絞り込みと同じ理由で、忘れても型エラーにもテスト失敗にもならず、削除済みの行が見えるだけだから。`purgeOwnedData()` だけが唯一の意図的な例外で、呼び出し元はアカウント削除のみ。

アカウント削除は Better Auth の **`beforeDelete`** で行う。`afterDelete` ではない —— FKがNO ACTIONなので、先にuser行を消そうとすると失敗し、`afterDelete`には到達しない。Better Auth自身の session / account は `user` からcascadeする（ADR 0013の例外）。

## Alternatives considered

- **全て物理削除のまま**: 最も単純でクエリも増えない。ただし誤削除からの復帰手段が永久に無く、D4を「決めていない」から「決めた」に変えるだけの価値が薄い。
- **全て論理削除（アカウントも）**: 保持義務には強い。ただし**別途パージ処理を作らない限り「削除しました」が事実と違う状態**になり、cronトリガーが前提になる。今それを抱える理由が無い。
- **論理削除だがUndoは後回し**: `deletedAt` だけ先に入れる案。ユーザーから見て何も変わらないのに全クエリにフィルタが増えるだけなので、費用だけ先払いすることになる。

## Consequences

- 全ての読み取りに2つ目の不可視フィルタが増えた。リポジトリに閉じているので忘れようがないが、**新しいメソッドを足すときは `deletedAt` も忘れないこと**（ADR 0014のオーナー列と同じ注意）。
- **論理削除された行は溜まり続ける。** 今はパージ処理が無く、増え続けるとD1の10GB上限とrows_read課金に効いてくる。「ゴミ箱を空にする」または保持期間を過ぎた行の定期削除は未着手（マップ3-3）。
- ゴミ箱のUIは無い。復元できるのは削除直後のtoastからだけで、閉じてしまうと（APIを直接叩く以外に）復元手段が無い。
- アカウント削除は**パスワードまたは「fresh」なセッション**を要求する。Better Authの `session.freshAge` は既定24時間なので、**サインイン直後の24時間はパスワード無しでも削除できる**。UIは常にパスワードを求めるが、APIの契約はそれより緩い。テストにその契約を明示してある。厳しくするなら`freshAge`を縮める判断が別途要る。
- メール確認を伴う削除フロー（`sendDeleteAccountVerification`）は使っていない。メール基盤が無いため（ADR 0013）。

## Confirmation

`test/worker/account-deletion.test.ts` が通ること。特に「論理削除済みの行も含めて消える」「他のユーザーは無傷」の2本。`src/worker/db/repo.ts` に `deletedAt` を見ていない読み取りメソッドが無いこと（例外は `purgeOwnedData`）。
