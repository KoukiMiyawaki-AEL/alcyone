# ドキュメント規約

コードやコミットログには残らない「何を作っていてなぜか」「外部から見た仕様は何か」を
記録する場所。

## 何がどこにあるか

| 場所 | 役割 | 読者 |
|---|---|---|
| [`README.md`](../README.md)（直下） | 入口。これは何か、セットアップ、どこを読むか | 初めて開いた人 |
| [`CLAUDE.md`](../CLAUDE.md)（直下） | コードの書き方と、壊してはいけないもの | このコードベースで書く人 |
| [`docs/design/`](./design/) | 何を作っていて、どういう設計か | 設計を読む人 |
| [`docs/api/`](./api/) | APIの外部仕様 | 参照する人 |
| [`docs/pii.md`](./pii.md) | 保持している個人情報と、その消し方 | 参照する人 |
| [`docs/deploy.md`](./deploy.md) | デプロイの手順。**まだ実施していない** | 参照する人 |
| [`docs/dev-accounts.md`](./dev-accounts.md) | ローカルで画面を触るためのアカウント | 参照する人 |

`docs/design/` は [`overview.md`](./design/overview.md) が入口で、
そこから4本の深掘りに分かれる。

## 文書は現在の設計を述べる

**すべての文書は現在形で書く。** 「以前はこうだった」「Xを検討して却下した」は書かない。

- 設計が変わったら、**文書を書き換える**。追記や履歴の節を作らない。
- **なぜ変わったかはgitに聞く。** 決定の経緯はコミットに残る。

この規則には帰結がある：**「なぜこうなっていないのか」に答える文書は、
リポジトリに存在しない。** 却下した選択肢を知りたければ `git log` を辿ることになる。
それを承知のうえで、**読む人が常に1つの現在形の記述だけを見る**ことを優先している。

**ただし制約とNon-Goalsは書く。** 「一般ユーザーは自分のプロジェクトを持てない」は
不具合ではなく決定で、知らない人はそれをバグとして「直す」。できないことは設計の内容である。

## 書く場所の使い分け

- **`CLAUDE.md`** は「今この瞬間、コードをどう書くべきか」に答える。規則と、その理由を1行。
- **`docs/design/`** は「何を作っていて、どういう設計か」に答える。
  規則の背景、原則、サブシステムの形。
- **`CLAUDE.md` は規則と1行の理由、`docs/design/` は同じ規則の背景。** 重なるのは意図的で、
  規則だけを読んだ人が理由を推測して回避するのを防ぐため。ただし**説明を厚くするのは
  design側だけ**にする。

実装と文書が食い違うようになったら、**文書を直す**。
