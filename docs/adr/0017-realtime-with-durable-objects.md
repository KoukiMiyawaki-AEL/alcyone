# 0017. リアルタイム更新をDurable Objects + WebSocketで実装する

## Status

Accepted

## Context

このADRは**トリガーが発火していない状態で書かれている**。最初にそれを書いておく。

[service-readiness-map](../design/service-readiness-map.md)の3-5「リアルタイム同期」のトリガーは
**「1テナントで同時編集が起きるとき」**で、Projectは単一オーナー（[ADR 0014](./0014-user-owned-projects.md)）
なので同時編集は構造的にまだ起きない。マップの規約に従えば、これは着手しない側の項目である。

動いた理由は別にある。現在の作業目標が**「この技術スタックで学べることを網羅する」**であり、
Durable Objectsは**Cloudflareで最も特徴的で、かつこのリポジトリで最も検証されていないプリミティブ**
だった。つまり駆動しているのはプロダクトの必要ではなく、検証の目的
（[ADR 0010](./0010-alcyone-as-proving-ground.md)の位置づけ）である。

ただし、単一オーナーでも実利はある。**同じユーザーの2枚目のタブ・2台目の端末**は今日から存在しうる。
これは「同時編集」ではなく「同一人物の複数ビュー」で、競合解決を必要としない一番易しい形の
リアルタイムである。**難しい部分（競合解決・プレゼンス・権限）は依然として未着手**であり、
これを入れたことで3-5が済んだことにはならない。

## Decision

**ユーザーごとに1つのDurable Objectを置き、WebSocketで「変わった」だけを配る。**

### なぜDurable Objectsが必要なのか

Workerの1回の実行は、他の実行が存在することを知らない。だから「別のタブに知らせる」が
**そもそも表現できない**。Durable Objectは名前で指定でき単一インスタンスなので、
「このユーザーの接続が集まる場所」という概念が初めて書ける。ここが本質で、
KVやD1では代替にならない（どちらも接続を保持できない）。

### 送るのは「変わった」だけで、変更内容は送らない

`{ "type": "invalidate" }` の1種類しか送らない。変更内容を載せると、
**データを知る経路が2つできて、いずれ食い違う**。受信側は `router.invalidate()` で
再取得するだけにしてあり、これはリクエスト1回のコストで**絶対にずれない**。
DBが唯一の真実であり続ける（[ADR 0004](./0004-router-loader-over-query.md)の
loader中心の方針とも噛み合う）。

副作用として、このDurable Objectは**アプリのデータを一切持たない**。
持たないので、壊してデータを失う経路が存在しない。

### Hibernation APIを使う（`acceptWebSocket`、`accept` ではない）

`accept()` だと接続がある間オブジェクトがメモリに残り課金される。
`acceptWebSocket()` なら接続リストをランタイムが持つので、
**開いたまま放置されたタブは何も起きていない間コストゼロ**。
一日開いたままのタブは普通にあるので、既定の選択にする。
`test/worker/realtime.test.ts` に `getWebSockets()` の本数を見るテストがあり、
`accept()` に戻すと落ちる。

### ブロードキャストはハンドラではなくミドルウェアから撃つ

各ミューテーションハンドラに `notifyUser()` を書くと、**12箇所は12回忘れる機会**で、
忘れた1箇所は「静かに古いUI」として現れる。
リポジトリで所有スコープを1箇所にまとめたのと同じ理由で、`/api/*` の後処理ミドルウェアに置く。

条件は「非GET かつ `c.res.ok`」。**拒否された書き込みで再取得を促すのは純粋なノイズ**である。

`ctx.waitUntil()` に載せてレスポンス経路では待たない。
**すでにコミットされた書き込みが、通知の失敗で失敗してはならない。**
リアルタイムは最適化であって、データはもう安全である。

### 認証はCookieに乗る

ブラウザはWebSocketのハンドshakeにヘッダを付けられないが、**Cookieは送る**。
なので `/api/realtime` は他のエンドポイントと同じセッションガードの後ろに置くだけでよく、
専用のトークン発行は要らない。宛先は `idFromName(userId)` なので、
**他人のチャンネルを指定する余地が構造的に無い**。

## Consequences

### 得たもの

- 別タブ・別端末が自動で追いつく。
- Durable Objects / WebSocket Hibernation / `waitUntil` / `runInDurableObject` が実際に動く形で入った。
- テストが**2つの層に分かれた**: チャンネル単体（配信・分離・hibernation）はworkerテスト、
  「別タブに実際に現れる」はE2E。後者でしか分からない不具合が実際に1件出た（下記）。

### 見つかった不具合 —— router contextから読むと繋がらない

最初は `Route.useRouteContext()` からセッションを読み、
「ルートガードと同じ信号で開閉するので一貫している」というコメントまで書いた。
**これは間違いで、E2Eが即座に落とした。**

TanStack Routerのcontextは**matchesが再解決されたときにしか再計算されない**。
`RouterProvider` に新しい `context` を渡してもコンポーネントは再レンダリングされない。
初回ロードでは「セッション取得中（`user` は null）」の状態でrouteが解決し、
そのあと何もnavigateしないので、**ソケットは永久に開かない**。
サインアップ直後は画面遷移が起きるので偶然動いてしまい、
タブを2枚開くE2Eだけが露出させた。

ルートガードが同じ問題を踏まないのは、**ガードはnavigate時にしか走らない**からである。

修正は `useAuth()`（Reactのcontext）から読むこと。教訓は
**「ルータのcontextは購読ではない」**で、Reactの再レンダリングを当てにする用途には使えない。

### E2Eの脆さが露出した（この機能の責任ではない）

この機能を入れた直後にE2Eが不安定になり、最初は原因をこの機能だと結論づけた。**それも間違いだった。**
フックを切った対照実験で同じように落ちたので、原因は既存の脆さだった。

真因は**Viteのdevサーバがルートを遅延コンパイルすること**。`webServer.url` は `/` が応答するまでしか
待たず、TanStack Routerはnavigateされて初めてそのルートのチャンクを取りに行く。
結果、**各specファイルの先頭テストだけが変換コストを計測付きのアサーション内で払い**、
負荷が乗ると5秒のexpectタイムアウトを超えていた。同じファイルの後続は1秒で通るので、
「先頭だけ落ちる」という特徴的な形になる。

`test/e2e/warm-up.ts`（`globalSetup`）で全ルートを事前に1回踏むことにした。
不安定さが「起動が少し遅い」に変わる。

**もう一つの運用上の教訓**: E2Eの実行中に別のコマンドを走らせると、実行時間が数十倍になる
（このセッションで2回起きた）。測るときは単独で走らせる。

### 残っている穴

- **プレゼンス無し**。「誰が見ているか」は分からない。
- **競合解決無し**。最後の書き込みが勝つ。同時編集が来たときに効くのはここで、
  3-5が本当に必要とするのはこの部分である。
- **配信保証無し**。ソケットが落ちている間の変更は失われる。再接続時に全体を再取得するので
  結果は正しくなるが、それは「取りこぼしても再取得で直る」設計に依存している。
- **ファンアウトの上限を測っていない**。1ユーザーがタブを100枚開いたときの挙動は未検証。
- 開発時のStrictMode二重マウントで、確立前のソケットを1本閉じる警告がコンソールに出る。
  再接続するので無害だが、消していない。
