# Cloudflareのプリミティブ

このアプリは、Workers上でサービスを運営するのに必要になるプリミティブを一通り使っている。
**それが目的だからである**（[`overview.md`](./overview.md)）。以下は、それぞれを
「何のために」使い、「何に注意が要るか」の記録。

`wrangler.jsonc` のbindings：`DB` / `SHARE_CACHE` / `ATTACHMENTS` / `OBJECT_CLEANUP`
（＋DLQ）/ `DATA_EXPORT` / `USER_CHANNEL` / `ANALYTICS` / 3つのRate Limiter。

## D1

主データストア。詳細は [`data-model.md`](./data-model.md)。

**リクエストごとにD1 Sessionを開く。** 読み取りレプリカは書き込みに遅れうるので、
「保存した直後に一覧が古い」が起きる。Sessions APIのbookmarkをCookieに載せて往復させ、
**同じ利用者の後続の読み取りが、自分の書き込みを見たレプリカに当たる**ようにしている
（`src/worker/db/session.ts`）。

## Durable Objects — リアルタイム更新

ユーザーごとに1つのDurable Object（`USER_CHANNEL`）を持ち、WebSocketで
「あなたのデータが変わった」とだけ伝える。受け取った画面は `router.invalidate()` で
自分で取り直す——**変更内容は流さない**ので、権限の判定がクライアント側に漏れない。

**WebSocket hibernationを使う**（`acceptWebSocket`）。接続を保持したままメモリから
退避できるので、開きっぱなしのタブが課金され続けない。

**セッションをReactの再レンダリングの条件に使うときは `useAuth()` から読む。**
`Route.useRouteContext()` はmatchesが再解決されたときにしか更新されないので、
「セッションが後から届いたら接続を始める」用途では**初回ロードで永久に発火しない**。

**サブリクエスト由来のレスポンスはヘッダが不変**なので、Cookieを足すときは
レスポンスを組み直す——ただし 101（WebSocket）だけは組み直せない。

## Queues — R2オブジェクトの削除

添付ファイルの実体はR2にあり、**行とオブジェクトは別々に消す必要がある**。
削除のたびに同期でR2を叩くと、失敗したときに行だけ消えて実体が残る。

そこで**行を先に消し、鍵をキューに送る**。消費側（`src/worker/object-cleanup.ts`）が
R2から削除し、失敗したメッセージはDLQに落ちる。

順序は決まっている：**アップロードは所有権チェックのあとに書く**（先に書くと、
どの行からも参照されないオブジェクトが残る）。**削除は行を先に消す**（先にオブジェクトを
消して失敗すると、実体の無い行が残る）。

R2の一覧は**1回あたり1000鍵**しか返さないので、退会時のように大量に消す経路では
カーソルで回し切ること。

## Workflows — データエクスポート

アカウントのデータ一式をJSONにしてR2へ書き、署名付きURLで渡す。
リクエストの寿命より長くかかりうるので、`WorkflowEntrypoint` で段階に分ける
（`src/worker/data-export.ts`）。各 `step.do` は独立に再試行される。

## Workers KV — 公開共有ページのキャッシュ

`/s/$token` は認証を持たない人が開くので、**D1に触らせずに答えられる**ようにする。
KVは結果整合なので、共有を解除した直後にキャッシュが残りうる——**解除時に明示的に消す**。

## R2 — 添付ファイル

鍵は推測できない値にする。R2にはパスベースの権限が無いので、
**鍵を知っていることが実質的な認可になる**。アップロードはユーザー単位でレート制限し、
サイズは5MBで切る（Workerのメモリに収まる範囲で扱う）。

## Analytics Engine — 計測

公開共有ページの閲覧数、キャッシュのヒット率、エラー率を書く。
**イベントの形は `src/worker/analytics.ts` で固定**し、呼び出し側が列の意味を決めない。

**計測の失敗でリクエストを壊さない。** 書き込みは例外を飲み込むラッパを通す——
`onError` の中から投げる例外には行き場が無い。

## Rate Limiting — 濫用のコストを上げる

3つのlimiterを使い分ける：認証系（IP単位）、アップロード（ユーザー単位）、
公開エンドポイント（IP単位）。

**location単位かつ結果整合で、Cloudflare自身が「正確な計上には使うな」と明記している。**
割当量ではなく、濫用のコストを上げるためのもの。

## Cron Triggers — 保持期限のパージ

論理削除から30日経った行を物理削除する（`src/worker/scheduled.ts`）。
**ユーザーのいない処理は `createRepo` を使わない**——あれは `ownerId` で必ず絞るためのもので、
ユーザーを持たないクエリは `src/worker/db/maintenance.ts` に置く（名前で区別が付くようにしてある）。

## 観測

`observability` を有効にし、**構造化JSONで、必ず `requestId` を含めて**ログを出す
（Workersのobservabilityでフィールド検索し、1リクエストのログを束ねるため）。

**リクエストボディとヘッダはログに出さない。** 一度Workers Logsに入ったPIIは
保持期間内は消せない（[`../pii.md`](../pii.md)）。
