# 0027. Todoにコメントと、書き換えられない変更履歴を持たせる

## Status

Accepted

## Context

[service-readiness-map](../design/service-readiness-map.md)の**D5**は、監査証跡を
一方通行のドアとして記録していた。抜粋:

> **遡って作れない。** さらにこのスタック固有の罠がある: 「todoを1件insert + 監査行を1件insert」を
> `db.transaction()` で囲むと**型は通るが実行時に落ちる**。D1に対話的トランザクションが無いため。
> 原子性の手段は `db.batch()` だけ。
>
> **今できる最小の一手**: 書き込みを1つの経路に集約し、**`batch()` に載せられる形にしておく**。

書き込みは既に `createRepo` の1経路に集約してあり、[ADR 0024](./0024-todo-status-instead-of-completed.md)で
更新エンドポイントも1本に統合済みだった。**D5が「今のうちにやっておけ」と言っていた準備は済んでいた**ので、
残っていたのは履歴そのものを書くことだけである。

同じく3-5の「履歴・アクティビティ表示」は、着手条件が**「D5に着手したとき」**だった。

## Decision

### コメントと履歴は別のテーブルにする

同じ「アクティビティ」に見えるので1つにまとめたくなるが、**性質が正反対**である。

| | コメント | 履歴 |
|---|---|---|
| 編集 | できる（誤字も、間違った内容も） | **できない** |
| 削除 | できる（論理削除） | できない |
| 書く主体 | 人 | システム |

1つのテーブルに入れると、**追記専用という唯一の性質を履歴が失う**。
書き換えられる監査証跡は監査証跡ではない。

画面では時系列に混ぜて出す（変更のすぐ上か下にその説明のコメントが来るのが普通なので、
2つのリストに分けると読む人が頭の中で合流させることになる）。混ぜるのは表示の話であって、
保存の話ではない。

### 履歴は「変更を記録してから変更する」を1つの `batch()` に載せる

素直に書くなら「現在の行を読む → 差分を計算する → 更新する + 履歴を書く」だが、
これは**2重に間違い**である。往復が1回増えるうえ、読みと書きの間に別のリクエストが
同じ行を変えると、**起きていない遷移が履歴に残る**。

代わりに、比較を `INSERT ... SELECT` の `WHERE` に入れた:

```sql
insert into todo_events (...)
select todos.id, ?, 'status', todos.status, ?, ?
from todos
where todos.id = ? and todos.status is not ? and <所有者>
```

値が変わっていなければSELECTが0行を返し、**何も挿入されない**。
古い値は**使う瞬間に読まれる**ので、隙間が存在しない。
そして履歴の挿入と更新は同じ `batch()` に入り、順序は**履歴が先**——
UPDATEが走った瞬間に古い値は存在しなくなるからである。

`db.transaction()` は使えない。**型が通って実行時に落ちる**というD5が予告した通りで、
これは実装前から分かっていた唯一の理由で選択肢から外してある。

### `is not` であって `<>` ではない

SQLの不等号はNULLを伝播する。`dueAt <> '2026-12-01'` は `dueAt` がNULLのとき**NULLを返し、偽として扱われる**。
つまり `<>` で書くと、**日付を設定した/外した履歴だけが静かに欠落する**。
テストがその2件を直接見ている。

### 記録するのは日程と状態であって、文章ではない

`description` の編集は履歴に残さない。散文の変更履歴はノイズで、
**見るべき変更をその中に埋めてしまう**。メモそのものが記録である。

### コメントは `authorId` を持つ

Projectは単一オーナー（[ADR 0014](./0014-user-owned-projects.md)）なので、
今日は書き手が常に所有者と一致する。それでも記録するのは、
**一致しなくなった日にこれらのコメントが生き残るため**である。
後から誰が書いたかを推定するのは、推測を記録することになる。

編集・削除の条件は `authorId = 自分` と `todoの所有者 = 自分` の両方。
今は同じ条件だが、**偶然一致しているだけの規則は規則ではない**。

### 外部キーの順序を、作った同じコミットで3箇所に入れた

`todo_comments` と `todo_events` は `todos` を NO ACTION で参照する。これは
[ADR 0019](./0019-object-cleanup-queue.md)で夜間パージを全滅させ、
[ADR 0022](./0022-share-links-cached-in-kv.md)で踏む寸前だったのと同じ罠である。

今回は保持期限のパージ、退会時のパージ、テストの `resetAll` の3つを、
**テーブルを作ったコミットで**同時に直した。加えて、パージのバッチが増えたことで
呼び出し側の位置指定がずれたので、**結果を名前で返す**ようにした——
文を1つ足すたびに全呼び出し元が静かにずれる形をやめるため。

## 追記: 1回の保存を1つのまとまりとして表す（migration 0015）

最初の実装は**1フィールド1行**で、それぞれが独立していた。しかし詳細フォームは
毎回全項目を送るので、実際の1回の保存はたいてい複数フィールドを変える。
結果、**1つの操作が3行に見える**——「何をしたか」ではなく「何が変わったか」の羅列になっていた。

`todo_events.revisionId` を足し、**同じ保存で書かれた行に同じidを与える**。
画面はそれを1つのまとまりとして描く。

idは `crypto.randomUUID()` で作る。**タイムスタンプで代用しない**——同じミリ秒に起きた
2つの保存が1つに融合するし、「時計が偶然一致したから同じ操作」というのは
データがどこにも書いていない推測である。生成したidなら、それを明示的に述べている。

### コメントを変更に添えられるようにした

「ブロック中にした、理由はAPIレビュー待ち」は**1つの出来事**である。
別々に投稿させると、時刻が近いだけの2つになる。

`PATCH /api/todos/:id` が任意の `comment` を受け取り、
**同じbatchの中で**同じ `revisionId` を持つコメントを作る。
`todo_comments.revisionId` はnullableで、**そのnullが意味を持つ**——
revisionを持たないコメントはタスクについての発言、持つコメントはその変更の理由である。

原子性がここで効く: 変更が失敗すればコメントも書かれない。
**起きなかった変更の理由が残る**のは、理由が無いより悪い。

### 変更に添えたコメントは編集できない

それはその保存の記録の一部である。後から書き換えられると、
**述べられた理由が実際に起きたことから離れていく**。単独のコメントは今まで通り編集できる。

## Consequences

### 得たもの

- D5が「遡って作れない」と言っていたものが存在するようになった。
- 3-5の「履歴・アクティビティ表示」が埋まった。
- `batch()` を原子性のために使う実例ができた（これまでは順序のためだけだった）。

### 残っている穴

- **`created` は挿入とは別のbatch**。idが決まるまで書けないため。
  途中で落ちるとタスクだけが残り、履歴が1件ぶん短くなる。逆よりはましという判断。
- **プロジェクトの変更は履歴に残らない。** 名前の変更も削除も記録されない。
- **履歴に保持期限が無い。** タスクが消えるときに一緒に消えるだけで、それ以外では増え続ける。
- **変更が無かった保存に添えたコメントは、行き場を失って独立した発言になる。**
  捨てるよりましという判断だが、書いた人の意図とはずれる。
- **アクティビティはURLに現れない。** ダイアログの中だけなので、特定のコメントへリンクできない。
  loader経由にしなかったのは、一覧の全行が開かれもしないパネルの取得を払うことになるため。
- **他人のコメントはまだ存在しえない。** 「ユーザー毎」が意味を持つのは
  1つのProjectに複数人が届くようになってからで、それは組織テナンシー（CLAUDE.mdのNot Yet）待ちである。
