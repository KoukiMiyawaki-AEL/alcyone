# 0036. 3つのロールが「何のためのもの」かを決める（見える範囲と、変えられる範囲を分ける）

## Status

Accepted（[ADR 0031](./0031-project-membership-and-roles.md)の2つのスコープと、
[ADR 0034](./0034-three-account-roles-and-a-screen-that-creates-them.md)の3段階を、
**アクターの定義**として言い直す）

## Context

[ADR 0034](./0034-three-account-roles-and-a-screen-that-creates-them.md)で
`owner` / `admin` / `member` を入れたが、決めたのは**強さの順序**だけだった。
「管理者は管理者である」以上のことを言っていない。

その結果、実装は素朴に「上位ほど何でもできる」になっていた。
**管理者は、参加していないプロジェクトのタスクを読め、参加者を入れ替えられた。**
これは事実上「全プロジェクトのオーナー」であり、システムのオーナーと区別が付かない。

## Decision

ロールを、強さの段階ではなく**役割**として定義する。

| ロール | 何のためのアクターか | 見える | 設定を変えられる |
|---|---|---|---|
| `owner` | **システム**の管理 | 全プロジェクト | 全プロジェクト |
| `admin` | **参加しているプロジェクト**の設定管理 | 全プロジェクト | 参加しているものだけ |
| `member` | プロジェクトに参加して作業する | 参加しているものだけ | 作成したものだけ |

（表の「設定」は参加者の増減・削除・共有リンク。タスクの読み書きは「見える」側。）

### 見える範囲は広く、変えられる範囲は狭く

多くのシステムと逆向きで、意図的である。

- **管理者が全プロジェクトを見られるのは、探せる必要があるから。**
  「あのプロジェクトの参加者を直して」と言われて、そのプロジェクトに辿り着けないなら
  役割が成立しない。
- **管理者が参加していないプロジェクトの設定を変えられないのは、ロールが入口ではないから。**
  誰かが参加者として追加する必要があり、**その行が「誰が・いつ」を残す**。
  ロールだけで入れると、何も残らない。

`accessibleProjectIds()`（見る）と `ownedProjectIds()`（変える）という
[ADR 0031](./0031-project-membership-and-roles.md)の2関数はそのまま。
**変わったのは、それぞれにロールがどう効くかだけ**である——
2つに集約してあったので、この変更もその2箇所で済んだ。

```
accessibleProjectIds  = 作成者 or 参加者 or (admin または owner)
ownedProjectIds       = owner ? 全部 : (作成者 or (admin かつ 参加者))
```

### 「変えられるか」はサーバが答える

`GET /api/projects/:id/members` の `canManage` は、**書き込み側が使うのと同じクエリ**
（`projects.findManageable`）から返す。「作成者、またはシステムのオーナー、または参加している管理者」は
条件が3つあり、クライアントが組み直すと**APIが拒むボタンをUIが出す**。

### 参加者を外すと、その人の担当も外れる

「除外」が行の削除だけだと、**開けなくなった人の名前が担当欄に残る**。
誰もやっていないタスクが、誰かがやっているように表示される。

1つのbatchで「履歴を書く → 担当を外す → 参加行を消す」。
履歴が先で、**同じSELECTから書く**——ハンドラで読んでから書くと、
その間に別のリクエストが入る余地ができる（[ADR 0027](./0027-comments-and-append-only-history.md)）。

**3つの文すべてに同じ権限チェックを載せる。** 片方だけだと、
権限のない呼び出しが「担当だけ外して、行は消せずに失敗する」ことになる。

### 作成者は名前で出す

参加者一覧は全員を名前で出すのに、**消せない1人だけが「プロジェクトの作成者」という無名の役割**
だった。バグに見える。名前とアドレスを出し、他の行がボタンを持つ位置にバッジを置く。

## Consequences

### 得たもの

- 「管理者」が、システムのオーナーとは別の意味を持つようになった。
- プロジェクトへの参加は、**必ず誰かが行を作る**ことでしか起きない。ロールでは入れない。
- 除外がタスクの担当にまで届くようになった。

### 残っている穴

- **管理者は自分を参加者に追加できない。** 追加できるのは、そのプロジェクトを
  管理できる人（作成者・システムのオーナー・参加している管理者）だけ。
  意図どおりだが、「管理者に見てもらう」には誰かの操作が要る。
- **アカウントの作成と権限変更は、まだ管理者にもできる**
  （[ADR 0034](./0034-three-account-roles-and-a-screen-that-creates-them.md)のまま）。
  「システムの管理はオーナー」という線を厳密に引くなら、ここも動かすことになる。
  今回は動かしていない。
- **参加者に段階が無い。** 閲覧のみ、といった中間はまだ無い。
- **除外の履歴は担当解除だけ。** 「誰がいつ外されたか」は
  `project_members` の行が消えるだけで、どこにも残らない。
