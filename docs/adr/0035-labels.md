# 0035. ラベルを入れる（ステータスでも担当者でも表せない軸）

## Status

Accepted

## Context

タスクは**ステータスを1つ**、**担当者を1人**、**親を1つ**しか持てない。
これは正しい制約だが、そこに乗らない事実の置き場所が無かった。

- 「顧客から報告された」
- 「デザインの判断待ち」
- 「リリース 2.4 に入れる」

どれもステータスではないし担当者でもない。**多対多で、任意個**。
今までこの手の情報はタイトルに書くしかなく、
`[要調査] APIのタイムアウト` のような**検索でしか使えない構造**になっていた。

## Decision

### `labels` と `todo_labels`

ラベルは**プロジェクトに属する**。アカウントではない——
プロジェクトの語彙はそのプロジェクトのもので、他のプロジェクトに持ち込む意味は薄い。

`(projectId, name)` に一意制約。同じプロジェクトに同名のラベルが2つあると、
チップの上では**区別する手がかりが無い**。

### 色は固定のパレット

自由なhexにしない。理由は2つ:

1. **12人が自由に選ぶと、同じような濁った青が12種類できる。** ボードが読めなくなる。
2. 各色はDesign Tokenで、**LightとDarkの両方の値を既に持っている**。
   選ぶ側が2回選ばずに、どちらのテーマでも読める。

値域はzodのenumとDBのCHECKの両方に置く（CLAUDE.mdの規約どおり）。

### 誰が作れるか —— タスクを触れる人

`accessibleProjectIds()`。参加者でも作れる。
**ラベルは仕事の整理の仕方**であって、カテゴリに名前を付けるのに
オーナーの許可が要るなら、それは整理ではなく事務手続きになる。

（`ownedProjectIds()`は「鍵を配る」側の権限で、これは違う質問である——
[ADR 0031](./0031-project-membership-and-roles.md)。）

### タスクに付けるのは「集合の置き換え」

`PUT /api/todos/:id/labels` に `{ labelIds }` を送る。追加/削除の列ではない。

差分だと、**2人が同時に編集したときに、どちらも選んでいない状態**に着地しうる。
集合なら「この画面が見ていた結果」がそのまま入る。

置き換えは1つのbatchで、削除→挿入の順。先に消すので**upsertが要らない**。

**挿入はinsert-from-selectで、タスクとラベルが同じプロジェクトかをJOINで検査する。**
外部キーは**存在**を検査するのであって**所属**ではない——
このリポジトリで4回目の同じ穴なので、最初からこう書いた。

### 一覧の絞り込みはWHEREに入れる

URLのsearch paramsに `label` を置く（他の絞り込みと同じ理由：リンクで共有でき、
リロードで残り、loaderが再実行される）。

**取得済みの行を隠すのではなく、SQLで絞る。** 隠すと、
「1ページ分取ってきて何件か隠す」ことになり、**次のページが隠した分だけ短くなる**。

**ステータスの絞り込みと違い、ラベルはどの表示でも生き残る。**
ステータスはボードの列そのものなので board では無効化するが、
ラベルは「どのタスクか」を絞るのであって「どう並べるか」ではない。
「このラベルだけのボード」は筋の通った要求である。

**数字だが存在しないid**は空の結果を返す。無視して全件返すと、
**画面が「絞り込んでいます」と言いながら絞り込まれていない行を出す**ことになる。
一方、**数字ですらない値**は`.catch()`で捨てる——手でURLを書き換えただけで
エラー画面になる必要はない。

### 履歴には残さない

`todo_events` は「1つのフィールドの前の値と後の値」を記録する形をしている
（[ADR 0027](./0027-comments-and-append-only-history.md)）。
ラベルは集合なので、この形に**入らない**。無理に入れると
「before: 3,7 / after: 7,9」のような、読めない行が増える。

正しくやるなら「付けた/外した」を1件ずつ記録する別の形が要る。今回はやらない。

## Consequences

### 得たもの

- ステータス・担当者・親のどれでも表せない区別が、構造として持てるようになった。
- 一覧・ボード・ガントのすべてで同じチップが同じ意味で出る。
- 絞り込みがURLに乗ったので、「このラベルの残件」がリンクで渡せる。

### 残っている穴

- **複数ラベルのAND/OR絞り込みができない。** 1つだけ。
- **履歴に残らない**（上記）。
- **プロジェクトをまたいだラベルが無い。** 「全社的に緊急」のような軸は表せない。
- **並び順は名前順で固定。** 手で並べ替えられない。
- **ラベル名の変更APIはあるが、画面が無い。** 消して作り直すことになる。

### テストで気付いたこと

E2Eの各テストに配るIPアドレスが、**モジュールスコープのカウンタ**だった。
Playwrightが途中でこのモジュールを読み直すため、**カウンタが静かに1へ戻り**、
15個のテストが同じアドレスを共有していた。結果、認証のレート制限（IP単位・10回/分）に
まとめて当たり、**後続のspecファイルが軒並み落ちる**という形で現れる。

「今入れた機能がテストを壊した」ようにしか見えず、2度にわたって誤診の原因になった。
アドレスはテスト名のハッシュから引くようにした——モジュールの再読み込みでも、
実行のたびでも変わらないので、**衝突するなら常に同じ組み合わせで衝突する**。

見つけられたのは、サインアップのヘルパーに**レスポンスを見せる**ようにした直後だった。
それまでは「Projectsの見出しが出ない」としか言わず、429であることが分からなかった。
