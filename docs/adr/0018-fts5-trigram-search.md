# 0018. 全文検索をFTS5のtrigramトークナイザで実装する

## Status

Accepted

## Context

[service-readiness-map](../design/service-readiness-map.md)の3-5「全文検索」のトリガーは
**「検索が遅いと感じたら」**で、そもそも検索機能が無かったので発火しようがなかった。
[ADR 0017](./0017-realtime-with-durable-objects.md)と同じく、動機は
**「この技術スタックで学べることを網羅する」という作業目標**である。

ただしD1に固有の理由がひとつある。素朴な `LIKE '%q%'` はインデックスを使えず全走査になり、
**D1はスキャンした行数で課金する**（[ADR 0011](./0011-expand-contract-migrations.md)、
キーセットページネーションを選んだ理由と同じ性質）。つまり検索は、このスタックで
「動くが高い実装」と「安い実装」がはっきり分かれる数少ない機能である。

## Decision

**`tokenize='trigram'` のFTS5仮想テーブル + トリガー3本。** マイグレーションは手書き。

### なぜ既定の `unicode61` ではだめか —— 測って決めた

ローカルD1で実測した結果:

| トークナイザ | `設計ドキュメントを書く` に対して `設計` | `pagination` に対して `pagina` |
|---|---|---|
| `unicode61`（既定） | **0件** | 0件 |
| `trigram` | 0件（後述） | 1件 |

`unicode61` は非英数字で区切るので、**日本語には区切る場所が無い**。
`設計ドキュメントを書く` 全体が1トークンになり、部分では引けない。
UIに日本語が混在するこのアプリでは、既定のままだと検索は事実上機能しない。

`trigram` は3文字ごとの並びを索引するので、日本語も英語も部分一致で引ける。

### trigramの代償: 3文字未満は原理的に引けない

上の表で `trigram` でも `設計` が0件なのは、**2文字ではトライグラムを成さない**から。
3文字以上（`設計ド`、`ドキュメント`）なら引ける。これも実測。

**日本語で2文字の検索語は普通にある**ので、無視できない。
`toFtsQuery()` は3文字未満の語を落とし、**全部落ちたらnullを返す**。
呼び出し側はそのときだけ `LIKE` の全走査に落ちる。

高い方の経路を**フォールバックに限定した**のが要点で、逆ではない。
「短い検索語は高い」は受け入れるが、「全ての検索が高い」は受け入れない。

### FTS5のクエリ構文はユーザー入力を通してはいけない

`"`、`*`、`AND`、`(` はFTS5の構文である。素通しすると、
**`"` を検索した人には500が返る**（検索窓が壊れて見える）。
各語を `"` で囲み、内部の `"` は二重化してエスケープする。
語の間の空白は暗黙のANDになるので、全語を含む行だけが返る。

同じ理由で、`LIKE` 経路では `%` と `_` を `ESCAPE` 付きで無効化する。
`%` を検索した人に全件返してはいけない。

### 手書きマイグレーションであることの帰結

drizzle-kitはFTS5仮想テーブルもトリガーも表現できない。よって0009は手書きで、
`drizzle/meta/*_snapshot.json` にこれらは載らない。

**載らないので、drizzle-kitはこれらを消しも作りもしない。** これは概ね安全だが、
1箇所だけ危険がある: **`todos` を作り直すマイグレーション**（[ADR 0011](./0011-expand-contract-migrations.md)の
再構築パス）。SQLiteは `DROP TABLE` でそのテーブルのトリガーも落とすので、
**3本のトリガーが黙って消える**。索引は消えないので、クエリはエラーにならず、
ただ結果が少しずつ古くなる。**気づく手段が無い**種類の壊れ方である。

`test/worker/migrations.test.ts` がトリガー3本の存在を検証しており、
消えたらCIが赤くなる。

**追記**: この危険は[ADR 0024](./0024-todo-status-instead-of-completed.md)で**実際に発生した**。
`completed` を落とすために `todos` を作り直したところ、トリガーは予告通り消え、
`todos_fts` は行を保持したまま**エラーを出さずに古い結果を返し続けた**。
このテストが赤くなることも確認済み（復元を書かずに一度適用した）。`auth-schema.ts` のUNIQUE制約をインデックスに置き換えたのと同じ発想。

クエリ側のテーブル定義は `src/worker/db/fts.ts` に置き、**`schema.ts` からは export しない**。
drizzle-kitは `schema.ts` しか読まないので、これで「drizzleからクエリできるが、
drizzle-kitは存在を知らない」状態になる。

### ソフト削除された行は索引に残す

`deletedAt IS NULL` は `todos` に結合し直すときに効かせる。
索引が削除状態を知る必要が無くなり、**復元がインデックスに触らずに済む**。

## Consequences

### 見つかった既存の不具合 —— トリガーが `meta.changes` の意味を変えた

これが今回いちばん重要な発見である。

トリガーを入れた直後、`scheduled.test.ts` の「削除件数を報告する」テストが落ちた。
**purgeジョブが `meta.changes` を業務上の件数として使っていた**ためである。実測:

| 実際に削除した行 | `meta.changes` |
|---|---|
| todo 2件 | **6** |
| todo 2件 + project 1件（同一batch内） | todos **6** / projects **5** |

つまりD1の `meta.changes` は**トリガーによる書き込みを含み**、さらに
**`batch()` の中では文ごとに正しく割り当てられてすらいない**（projectsは実際1件なのに5）。

ジョブ自体は正しく動いていた。**嘘をついていたのは報告だけ**で、
これは長く生き残る種類のバグである（誰も見ないログに間違った数が出続ける）。

修正は `.returning({ id })` にして返ってきた行を数えること。正確で、
**追加のスキャンも要らない**（`SELECT count(*)` を足すのはD1の課金上むしろ悪手）。
再発防止のテストを `scheduled.test.ts` に置いた。

**一般化**: D1で `meta.changes` を業務上の件数として使ってはいけない。
トリガーが1本入っただけで意味が変わり、しかも静かに変わる。

### 残っている穴

- **ランキングが弱い。** trigramのbm25は語ベースの索引ほど意味を持たない。
  「よく一致した順」は名目上あるが、同点が普通に起きる（idで安定させている）。
- **ページングはランクを跨ぐと理論上ずれる。** `bm25()` は索引全体の統計に依存するので、
  ページを跨いで書き込みが起きると順位が動く。ランク順ページングに共通の性質で、
  受け入れて記録する。
- **索引が肥大する。** trigramは全ての3文字並びを持つので、`unicode61` より大きい。
  実測はしていない。行数が増えたら測る。
- **タイトルしか索引していない。** 説明文や添付ファイル名は対象外（そもそも説明文が無い）。
- **UIは1ページ目だけ。** 他の一覧と同じ制限。
- **todoのリネームAPIが無い。** 更新トリガーは今のところ保険で、
  タイトルを変える呼び出し元が存在しない（SQLレベルでテストしてある）。
