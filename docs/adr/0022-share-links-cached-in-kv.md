# 0022. 公開共有リンクを作り、その描画結果をKVにキャッシュする

## Status

Accepted

## Context

KVがこのスタックで最後まで未検証だった。ただし
**「KVを使うために題材を探す」は設計としては逆**なので、
KVが本当に向く形の機能を探した。

KVが向くのは、**読み取りが圧倒的に多く / 世界中に配られ / 少し古くても構わない**データである。
D1が向かないのはまさにここで、D1は1DBが単一スレッドで、スキャン行数で課金される。

その形にぴたりと当てはまるのが「プロジェクトの読み取り専用公開リンク」だった。
1人が発行し、多数が開き、内容は数十秒古くても誰も困らない。
加えて[ADR 0014](./0014-user-owned-projects.md)で「Projectはユーザー所有」と決めて以来、
**他人に見せる手段が1つも無かった**ので、機能としても穴を埋める。

## Decision

**D1が「リンクが存在するか」の権威。KVは描画結果のキャッシュ。**

この分担が肝で、逆にはしない。トークンをKVだけに持つと、
**取り消しがKVの結果整合に完全に依存する**ことになる。D1に行があるので、
取り消しは即座に効き、キャッシュはあくまで前段になる。

### KVの結果整合を、正直に受け入れる範囲で使う

`purgeSharedView()` はKVのキーを消すが、**KVの削除は即時ではない**。
レプリカは最大TTLぶん古い値を返し続けうる。つまり:

**共有リンクの取り消しは「1分以内に効く」であって「即座に効く」ではない。**

これを受け入れられるのは、TTLが60秒と短く、守っている対象が
**読み取り専用のタスク一覧**だからである。
取り消しが即座に効かなければならないものに、この構成を使ってはいけない——
そのときに必要な「毎回D1を見る」は、**まさにKVを入れて避けたことそのもの**である。

UIにもそう書いてある（「解除しても最大1分間だけ表示され続けることがあります」）。
**実装の都合を利用者に隠さない**方を選んだ。

### 公開ペイロードは行ではなく、選んで作る

`SharedView` はDBの行そのものではない。id・ownerId・createdAtは載せない。
**リンクを持っている人全員に渡るもの**なので、
「テーブルに列を足したら公開範囲が広がった」が起きない形にしておく。
テストが `alice@example.com` / `ownerId` / `projectId` の不在を直接見ている。

### 見つかったバグ: 外部キーは所有を検査しない

最初の実装は `INSERT INTO shares (token, projectId, ...) VALUES (...)` で、
**projectIdの所有を一切見ていなかった**。しかもコード上のコメントには
「外部キーで絞られる」と書いていた。**それは間違いで、テストが落として教えた。**

外部キーは**存在**を検査するのであって**所有**ではない。
つまり**サインインしている誰でも、他人のプロジェクトの公開リンクを発行できた**。
[ADR 0014](./0014-user-owned-projects.md)の作業でIDORを塞いだのと同じ穴を、
新しいテーブルで作り直していたことになる。

修正はinsert-from-selectにして、**所有を文の一部にする**こと:

```sql
insert into shares (token, projectId, createdAt)
select ?, projects.id, ? from projects
where projects.id = ? and projects.ownerId = ? and projects.deletedAt is null
```

所有していなければselectが0行を返し、何も挿入されない。
**リポジトリのメソッド自体が安全**という規律（`repo.ts`）を守るため、
ハンドラ側でのチェックにはしなかった。

drizzleのinsert-selectは列がテーブル定義と完全一致することを要求し、
autoincrementのidまで並べる必要が出るので、ここは生SQLで書いてある。

### レート制限はミドルウェアに置く（型のため）

`enforce()` は素の `Response` を返す。これをハンドラ内で `return` すると、
**そのルートのRPC型が丸ごと `unknown` に潰れ**、クライアントが全フィールドを失う。
`hc<AppType>` を使う以上、ハンドラの戻り値は `c.json(...)` の union に保つ必要がある。

### 取り消し済みと存在しないトークンは同じ応答

差があれば、**かつて有効だったトークンを探る手段**になる。テストで固定してある。

### 同じ形の外部キーバグを、先回りして塞いだ

`shares.projectId` は `projects.id` を参照する。つまり
[ADR 0019](./0019-object-cleanup-queue.md)で直した「添付があるとpurgeが全滅する」と
**同じ構造の罠**が、共有リンク付きプロジェクトでも起きる。
今回は起きる前にcronのバッチへ `shares` の削除を足した。
テストヘルパの `resetAll` も同じ理由で更新している（こちらは実際に落ちて気づいた）。

## Consequences

### 得たもの

- 他人に見せる手段ができた。
- KV（`get` / `put` with `expirationTtl` / `delete` / `cacheTtl` / `list`）が実際に入った。
- **KVとD1の役割分担が、言葉ではなくコードで示された。**
- 所有を検査していないINSERTという実バグを、公開前に潰した。

### 残っている穴

- **キャッシュはTTLでしか無効化されない。** タスクを編集しても、共有ページは最大1分古い。
  [ADR 0017](./0017-realtime-with-durable-objects.md)のミドルウェアは
  「変更があった」しか知らず、どのプロジェクトかを持っていないので、
  今の形では狙って消せない。
- **取り消しは1分以内であって即座ではない**（上記）。
- **閲覧数**は[ADR 0023](./0023-analytics-engine-events.md)で記録するようにした（本番でのみ読める）。
  誰がいつ開いたかは**意図的に記録していない**。
- **有効期限が無い。** 発行したリンクは取り消すまで生き続ける。
- **1プロジェクト1リンク。** 相手ごとに分けて発行し、片方だけ切ることはできない。
- **実Cloudflare上で動かしていない。** KVの結果整合はローカルのminiflareでは
  そもそも再現しないので、**上に書いた取り消しの遅延を観測できていない**。
  [ADR 0021](./0021-d1-sessions-for-read-replicas.md)と同じ種類の未検証である。
