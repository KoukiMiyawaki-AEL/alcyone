# alcyone — 全体像

## これは何か

**alcyoneは技術検証の台である。** Cloudflare Workers上のスタック
（React + TanStack Router + Hono + Drizzle ORM + D1）で実際にサービスを運営するなら
何が必要になるのかを、動くものを通して確かめるために作られている。

**題材としてタスク管理ツールを作っているが、タスク管理ツールが目的ではない。**
「Todoアプリとして良くする」ことは目標に入っていない。この区別は重要で、
これを知らずに読むと、数人規模のツールに Durable Objects と Queues と Workflows と
Analytics Engine が揃っている理由が説明できず、ただの過剰設計に見える。

ターゲットユーザー（B2B / B2C）は決めていない。どちらに転んでも困らない選択を優先し、
先に決めないと後戻りが高くつくものだけを個別に前倒しで判断する。

## 何ができるか

プロジェクトの下にタスクがあり、タスクは**概要・一覧・ボード・タイムライン**の4通りに並ぶ。

- タスクはステータス・担当者・開始日・期限日・優先度・説明・親子関係・関連・ラベル・
  コメント・変更履歴・添付ファイルを持つ
- プロジェクトは参加者を持ち、参加していない人からは見えない
- タスクは全文検索でき、プロジェクトを横断して「自分の担当」を1画面で見られる
- プロジェクトは公開リンクで読み取り専用に共有できる
- アカウントのデータは丸ごとエクスポートでき、退会すると完全に消える

## 設計の原則

この4つが、以降のすべての判断の下敷きになっている。

### 1. 境界は1箇所にだけ引く

「誰が何に触れるか」の判定は `src/worker/db/repo.ts` の2つの関数にしかない。
ハンドラは既に絞り込まれたクエリだけを受け取るので、**絞り込みを忘れる余地が無い**。

同じ形が随所にある：mutationは全て `src/lib/mutate.ts` を通り、失敗時の表示は1箇所にしかない。
画面の可視性は `AccessGate` 1つが決める。セッションを終える出口は `endSession()` 1つだけ。

**忘れると静かに壊れるものは、忘れられない場所に置く。**

### 2. 権限は文の一部にする

「このプロジェクトを触ってよいか」は、SQLの `WHERE` の中にある。
ハンドラが先に確認してから書くのではなく、**権限を満たさない書き込みは0行に一致して終わる**。

外部キーはこの役に立たない。外部キーが検査するのは**行が存在すること**であって、
**その行が呼び出し元のものであること**ではない。他人のidを渡した書き込みは、
外部キーを満たしたまま成立する。だから所属の検査は insert-from-select の `WHERE` に置く。

### 3. 判定と書き込みを2文に分けない

「最後のオーナーは降格できない」を「数える → 更新する」の2文で書くと、
最後の2人が同時に互いを降格できる隙間ができる。条件は `WHERE` に入れて1文にする。
D1に対話的トランザクションは無く、`batch()` しかないので、この形が唯一の一貫性の担保になる。

### 4. 拒否は1つの形で答える

権限が無い要求への答えは、常に `404 { error: "Not found" }`。
「存在しない」と「あなたのものではない」を書き分けると、**書き分けそのものが情報になる**。
クライアント側も分岐が1つで済む。

## 構成

```
ブラウザ ── SPA（React + TanStack Router）
              │  /api/* だけがWorkerに届く
              ▼
           Hono（src/worker/index.ts）
              │  全ハンドラが repo を経由
              ▼
           D1（Drizzle ORM）
```

単一のViteプロセスがSPAとWorkerを同時に動かす（`@cloudflare/vite-plugin`）。
`wrangler.jsonc` の `assets.run_worker_first: ["/api/*"]` により、**`/api/*` だけがWorkerに届き**、
それ以外はasset workerがSPAとして処理する（未知のパスは `index.html` にフォールバックし、
ルーティングはクライアント側で解決される）。

## 設計上の制約

**これらは不具合ではなく決定である。** 知らずに「直す」と、設計が崩れる。

- **一般ユーザーは自分のプロジェクトを持てない。** プロジェクトを作るのは管理者以上で、
  一般ユーザーは参加して働く。自分の担当プロジェクトに1人足すにも管理者を呼ぶ。
- **プロジェクトの譲渡ができない。** 作成者が管理者であり続ける。作成者が退会すると
  プロジェクトごと消える（参加者がいても消える）。
- **プロジェクトキーは作成時にしか決められない。** キーは `ALC` のような短い識別子で、
  タスクは画面上 `ALC-12` と表示される——口頭でもチャットでも指せるようにするためのもので、
  だからこそ**書き留められた参照の中にある**。変更経路そのものを用意していない。
  打ち間違えたら作り直す。
- **タスク番号はプロジェクト内の連番ではない。** `ALC-3, ALC-7` のように飛ぶ。
  行のidを使っているため。2つのタスクが同じ番号を持つことはない。
- **セッション中のロール変更は、画面にすぐ反映されない。** 降格された管理者は、
  リロードするまで管理画面が残る（データはサーバが拒否する）。
- **参加者に段階が無い。** 閲覧のみ、といった中間の権限は無い。
- **組織・チームという単位が無い。** プロジェクトは作成者と参加者だけを持つ。
- **ゴミ箱の画面が無い。** 復元できるのは削除直後のtoastからだけで、30日後に完全に消える。
- **ダッシュボード・ボード・タイムライン・概要にページ送りが無い。** 読み込んだ範囲だけを
  見せる（画面上に明記される）。カーソルがあるのはタスクの一覧とプロジェクト一覧だけ。
- **公開共有リンクの内容は最大60秒古い。** タスクを消しても、その1分は共有ページに残りうる
  （KVのキャッシュを消すのは共有を解除したときだけ）。

## 今はやらないこと

- TanStack Query（データ取得はルーターのloaderで足りている）
- Turborepo / Alchemy / Storybook / カバレッジ計測
- メール送信（そのためメール検証とパスワード再発行は無効。招待はアカウントがある人にだけ届く）
- 本番デプロイ。D1はローカル開発のみで、`wrangler.jsonc` の `database_id` はプレースホルダ。
  手順は [`../deploy.md`](../deploy.md) にある
