# 0020. データエクスポートをWorkflowsで実装する

## Status

Accepted

## Context

[service-readiness-map](../design/service-readiness-map.md)の3-7に
**「データポータビリティ（エクスポート）」**があり、状態は未着手だった。
[ADR 0015](./0015-soft-delete-items-hard-delete-accounts.md)で
「退会したら完全に削除する」を決めたので、**その対になる「持ち出せる」が無い**のは片手落ちである。

同時に、Workflowsがこのスタックで未検証だった。エクスポートは
**互いに依存する複数ステップ**で、途中から再開できることに意味がある処理なので、
QueuesではなくWorkflowsが適する題材になる。

QueuesとWorkflowsの使い分けは、実際に両方入れて初めてはっきりした:

| | Queues（[ADR 0019](./0019-object-cleanup-queue.md)） | Workflows（本ADR） |
|---|---|---|
| 仕事の形 | 独立した単位の集まり | 互いに依存する一連の手順 |
| 失敗したら | そのメッセージだけ再試行 | **完了した手順は飛ばして再開** |
| 状態 | 持たない | 各ステップの戻り値が永続化される |

「R2の鍵を消す」は前者、「読んで・書いて・目録を作る」は後者。

## Decision

**`DataExportWorkflow` が、ユーザーのデータをR2へJSONで書き出す。**

### ステップの戻り値は小さく保ち、実データはR2へ

Workflowsは**ステップの戻り値を永続化する**。つまり戻り値には上限がある。
行そのものを返す設計は、**デモ用アカウントでは動いて実データで壊れる**——
一番たちの悪い失敗の仕方をする。

なので各ステップは、R2に書いたうえで `{ name, key, count }` だけを返す。
バルクはR2、調整はWorkflow、という分担にする。

### エンティティごとに1ステップ

`projects` / `todos` / `attachments` を別ステップにしてある。
1つが失敗したときに**3つのクエリではなく1つだけをやり直す**ため。

ステップ名は再開時の同一性そのものである。**名前を変えると黙って再実行される**ので、
「何を作るか」で命名してある（`export projects` など）。

### manifestは最後に、単独で書く

manifestの存在が「エクスポートが完成した」の定義になる。
これがあれば、**そこに載っている部品は必ず既に存在する**と読み手が信じてよい。
順序を決めておかないと、半分書けたエクスポートと完成したものが区別できない。

`generatedAt` はステップの**中**で作る。外で作ると、再開のたびに時刻が書き換わって
「いつ時点のデータか」が嘘になる。

### 所有権はインスタンスIDではなくR2の鍵で確かめる

`instanceId` は呼び出し側が渡す値で、**所有を何も証明しない**
（連番ではないが、それは推測しにくいというだけで、認可ではない）。
鍵は `exports/{userId}/{instanceId}/{part}.json` の形でセッションのuser idから組み立てる。
**他人の鍵を組み立てる余地が構造的に無い**。

`part` はenumで、自由文字列にしない。**R2の鍵の一部になるので、
自由文字列は自分のprefixの外へ出る手段になる**。

### 論理削除された行も含める

エクスポートは他の一覧と違い `deletedAt` で絞らない。
**「まだ持っているが、見せないことにした」は、データ開示の答えとして間違っている。**
各行が自分の `deletedAt` を持つので、削除済みであることは見えるまま残る。

### エクスポートにも保持期限を設ける

エクスポートは**その時点の全データの複製**である。永久に置いておくと、
[ADR 0015](./0015-soft-delete-items-hard-delete-accounts.md)の保持ポリシーも、
論理削除の30日ウィンドウも、静かに無効になる。

行を持たないので、cronは**R2の `uploaded` を見て**期限切れを見つけ、
[ADR 0019](./0019-object-cleanup-queue.md)のキューへ渡す。

退会時にも同じprefixごと消す。**エクスポートはユーザー自身のデータを書き出したものなので、
残せば「アカウントを削除しました」が最も素朴な意味で嘘になる。**

## Consequences

### 得たもの

- マップ3-7のデータポータビリティが埋まり、退会（削除）と対になった。
- Workflows（`WorkflowEntrypoint` / `step.do` / インスタンスの状態取得）が実際に動く形で入った。
- **vitest-pool-workersでWorkflowsが実際に走る**ことを確認した（8テスト）。
  ローカルで完結して検証できるので、[ADR 0003](./0003-d1-local-only.md)の制約下でも扱える。

### 残っている穴

- **再開を実際に見ていない。** ステップの途中で失敗させて、完了済みのステップが
  飛ばされるところを観測していない。Workflowsを選んだ理由そのものが未検証で、
  ここが一番弱い。
- **UIはポーリング**（1秒×60回）。[ADR 0017](./0017-realtime-with-durable-objects.md)の
  チャンネルは「変更があった」しか配らず、エクスポートは何も変更しない。
  1画面のためにチャンネルへ2種類目のイベントを教えるより、ポーリングの方が小さいと判断した。
  60秒で諦めるが、**それは失敗ではなく待つのをやめただけ**で、文面もそう書いてある。
- **1つのZIPにまとまらない。** 部品ごとに別ファイルで、ダウンロードも別々。
  ZIP生成はWorker上で全体をメモリに載せることになるので、上限を測るまでやらない。
- **エクスポートの同時実行に制限が無い。** ボタンを連打すればインスタンスが増える。
  レート制限は `/api/auth/*` と添付アップロードにしか無い。
- **添付ファイルの中身は含まない**（メタデータのみ）。実ファイルまで入れると
  上のZIP問題に直結する。
