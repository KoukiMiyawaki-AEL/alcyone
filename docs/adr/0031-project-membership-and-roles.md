# 0031. プロジェクトに参加者を持たせ、管理者ロールを導入する（0014の単独所有を広げる）

## Status

Accepted（[ADR 0014](./0014-user-owned-projects.md)の「Projectは1人が所有する」を、
**所有を残したまま参加を足す**形で広げる）

## Context

[ADR 0014](./0014-user-owned-projects.md)はProjectを単独所有と決め、
組織単位のテナンシーはCLAUDE.mdの「Not Yet」に置いていた。その結果:

- コメントの `authorId` も履歴の `actorId` も、**常に所有者と同じ値**だった。
- 担当者の候補は**常に1人**で、[ADR 0028](./0028-display-names-and-assignees.md)は
  「候補が1人なのでこの列はほとんど無意味」と正直に書いていた。
- [ADR 0026](./0026-timeline-not-a-gantt-chart.md)は、リソース平準化ができない理由に
  「担当者が実質存在しない」を挙げていた。

つまり**この一歩を踏むまで、いくつかの機能は形だけ存在していた**。

## Decision

### スコープを2つに分ける

これがこのADRの中心である。

| 関数 | 誰が通るか | 何に使うか |
|---|---|---|
| `accessibleProjectIds()` | 所有者・参加者・管理者 | タスクの読み書き、コメント、履歴、関連 |
| `ownedProjectIds()` | 所有者・管理者 | プロジェクトの削除、共有リンク、参加者の変更 |

**混ぜると参加者が鍵を配れるようになる。** 参加者が参加者を追加できるなら、
それは実質的にプロジェクトを譲渡できるということで、
所有者と参加者を分ける理由そのものが消える。両方向をテストで固定してある。

### 変更が1箇所で済んだ理由

[ADR 0014](./0014-user-owned-projects.md)が「絞り込みを足す場所を1箇所にするため」に
リポジトリを作った。実際、14箇所の呼び出しは**すべて `ownedProjectIds()` を通っていた**ので、
「所有」から「到達可能」への拡張は**その関数を書き換えるだけ**だった。
散らばっていたら、付け忘れが型エラーにもテスト失敗にもならずに越境漏洩になっていた。

### ロールは Better Auth の `user` に置く

自前のテーブルに置くと、**行の無いアカウントが存在しうる**ようになり、
すべての検査が「行が無いとはどういう意味か」を決めることになる。

**セッションではなくDBから読む。** トークンに載せたロールは、
トークンが更新されるまで古い値を持ち続ける。

**APIからは設定できない。** Better Auth の `update-user` に `role` を渡しても
無視されることをテストで確認してある。全アカウントは `member` で始まり、
管理者は意図的な操作でしか生まれない。

### 所有者は参加者の行を持たない

所有者のアクセスは `projects.ownerId` から来る。行を作ると**食い違いうる2つの事実**になる
（行を消された所有者、持ち主が変わったのに残る行）。INSERTが明示的に拒む。

### 参加者の追加も insert-from-select

権限を文の一部にする。外部キーでは捕まらない——**存在**を検査するのであって
**権限**ではない。同じ形の穴をこのリポジトリで3回作っているので、今回は最初からこう書いた。

### 「変更できるか」はサーバが答える

`GET /api/projects/:id/members` が `canManage` を返す。クライアントが規則を再実装すると、
**APIが拒むボタンをUIが出す**ことになる。

## Consequences

### 得たもの

- `authorId` / `actorId` / `assigneeId` が、初めて所有者以外を指しうるようになった。
- 担当者の候補が複数になり、[ADR 0028](./0028-display-names-and-assignees.md)が
  「候補が1人」と書いていた制限が解けた。
- サイドバーがプロジェクト内の移動を担うようになった（表示の切り替えと設定）。

### 残っている穴

- **招待にはユーザー一覧が要り、それは管理者しか見られない。** 所有者だけでは誰も呼べない。
  メールでの招待が本来の入口だが、メール基盤が無い（[ADR 0013](./0013-better-auth.md)）。
- **管理者を作る手段がAPIに無い。** DBを直接触るしかない。
  これは意図的だが、運用手順としては未整備である。
- **参加者に段階が無い。** 閲覧のみ、といった中間の権限は無い。
- **プロジェクトの譲渡ができない。** 所有者が退会するとプロジェクトごと消える
  （[ADR 0015](./0015-soft-delete-items-hard-delete-accounts.md)）。参加者がいても消える。
- **参加者は共有リンクの存在を知れない。** 共有ダイアログは管理者側にしかない。
