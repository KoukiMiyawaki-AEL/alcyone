# 0019. R2オブジェクトの削除をQueuesに逃がす

## Status

Accepted

## Context

Queuesを触るために題材を探していたら、**既存の本物のバグ**が出てきた。
順序が逆で、こちらが主でQueuesが従である。

### 見つかったバグ: 添付が1つあるだけで、夜間のpurgeが全滅する

`attachments.todoId` は `todos.id` を **NO ACTION** で参照している（[ADR 0012](./0012-no-on-delete-cascade.md)）。
そして `purgeExpiredDeletions` は `todos` を消すが、**`attachments` には一切触れていなかった**。

つまり、添付ファイルを持つtodoが論理削除されて30日経つと:

```
D1_ERROR: FOREIGN KEY constraint failed
```

purgeは**単一のbatch**なので、この1行のせいで **全ユーザーの分が1件も削除されない**。
しかも症状は「誰も見ないcronのログにエラーが出る」だけで、
**アプリ上は何も起きない**。[ADR 0015](./0015-soft-delete-items-hard-delete-accounts.md)で
決めた保持ポリシーが、静かに機能しなくなる。

実測で確認してから直した（`test/worker/object-cleanup.test.ts` の
「completes instead of failing the whole run on a foreign key」がその回帰テスト）。

### そしてR2オブジェクトが取り残される

行を消しても、R2のオブジェクトは残る。**オブジェクトを指すものが何も無くなる**ので、
発見する手段が無いまま課金だけ続く。行を消す前に鍵を読んでおく必要がある。

しかしオブジェクトの削除は**件数に上限が無い**work であり、
cronのCPU予算とサブリクエスト予算に載せてよいものではない。ここでQueuesが要る。

## Decision

**purgeは「何が期限切れか」を決め、Queueが「オブジェクトを消す」。**

### 順序: 鍵をキューに渡してから、行を消す

どちらの順序にも失敗モードがある:

| 順序 | 途中で落ちたとき | 性質 |
|---|---|---|
| 行 → オブジェクト | オブジェクトが孤児になる | **見えない**。永久に課金される |
| オブジェクト → 行 | ダウンロードが404する行が残る | **見える**。直せる |

後者を選ぶ。これは[ADR 0015](./0015-soft-delete-items-hard-delete-accounts.md)の
アカウント削除が既に採っている選択と同じで、理由も同じ
（「残った行は回復可能、残ったオブジェクトは不可視」）。

キューへの送信は**awaitする**。キューの目的はオブジェクト削除を経路から外すことであって、
引き渡し自体を不確実にすることではない。送信が失敗したら行は消さず、次回のcronが再試行する。

### ack / retry はメッセージ単位

バッチ単位でretryすると、**99件の成功した削除をやり直して1件の失敗に辿り着く**ことになる。
最良で作業量が倍、最悪で収束しない。

retryが安全なのは、**存在しないオブジェクトの削除がエラーにならない**から
（R2の性質。テストで固定してある）。冪等でなければretryは使えない。

`max_retries: 3` のあとはdead letter queueへ。処理できないメッセージは、
retryを消費し続けるのをやめて**見える場所に出る**べきである。

### アカウント削除はキューに載せない

`deleteUser.beforeDelete` は今まで通り**その場で削除する**。
「あなたのデータは削除されました」は、レスポンスを返す時点で**真でなければならない**。
「そのうち消えます」ではGDPR的にも説明が苦しい。

ただしそこにも潜在バグがあった: **R2の `delete()` は1回あたり最大1000鍵**で、
それを超える添付を持つアカウントは**削除に失敗していた**。
`deleteObjectsNow()` で分割するようにした（キュー経路と同じ分割器を共有する）。

## Consequences

### 得たもの

- 保持ポリシーが実際に機能するようになった（添付があっても止まらない）。
- 孤児オブジェクトが出なくなった。
- Queues（producer / consumer / `queue()` ハンドラ / DLQ / メッセージ単位のack）が実際に動く形で入った。
- アカウント削除の1000鍵上限バグが塞がった。

### 検証できていないこと

- **DLQは宣言しただけで、実際に落ちたところを見ていない。** ローカルのminiflareで
  DLQに落ちる様子を確認していない。
- **実際のCloudflareアカウント上で動かしていない。** キューはローカルのminiflareでしか
  動かしておらず、これは[ADR 0003](./0003-d1-local-only.md)の制約がそのまま効いている。
- **バックプレッシャを測っていない。** 1回のpurgeで何万件の鍵が出たときに
  `sendBatch` のループがcronの予算に収まるかは未測定。鍵の件数が増えたら測る。
- **消費側の失敗が続いたときの可視化が無い。** ログには出るが、
  アラートは無い（マップ3-6のアラート項目はまだ未着手）。
