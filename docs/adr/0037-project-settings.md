# 0037. プロジェクトに設定を持たせる（3つのツールの共通項を採る）

## Status

Accepted

## Context

プロジェクトが持っていたのは `name` だけだった。作成フォームも入力欄が1つ。

つまり**「プロジェクトとは名前である」と画面が教えていた**。実際には、
どのツールでもプロジェクトはもう少し多くのことを言う。

## Decision

推測ではなく、実際のツールの設定項目を確認して共通項を採った。

| | Jira | Asana | Backlog |
|---|---|---|---|
| 名前 | ✓ | ✓ | ✓ |
| キー / 識別子 | ✓ | — | ✓ |
| 説明 | ✓ | ✓ | — |
| 色 / アバター | アバター | 色 | — |
| 期間（日付） | — | ✓ | — |
| アーカイブ | — | ✓ | ✓ |
| リード / 既定の担当者 | ✓ | — | — |

交差部分を入れる: **キー・説明・色・期間・アーカイブ**。
リード／既定の担当者は1つのツールにしか無かったので今回は入れていない。

### プロジェクトキー

`ALC-12` の `ALC`。英大文字・数字・アンダースコア、10文字まで
（Backlogは25文字だが、これは画面上で全タスクの前に付くので短くした）。

**作成時に決まり、あとから変えられない。** Jiraは「課題が存在するプロジェクトのキーは
変更できない」とし、Backlogは「登録間違い以外では変更しないことを推奨」——
理由は同じで、**キーは誰かが書き留めたあらゆる参照の中にある**。
警告付きの変更経路を用意するより、経路そのものを作らないことにした。

名前から自動で提案するが、**規則ではなく提案**。日本語の名前からは何も出ないし、
"Design system" は DESIGNSYST になる——どちらも人が選ぶ文字列ではない。

タスク番号は**プロジェクト内の連番ではなく、行のid**である。Jira/Backlogは
プロジェクトごとに1から数えるが、それには採番用の列と競合時の再試行が要る。
そのため `ALC-3, ALC-7, ALC-9` のように飛ぶ。**2つのタスクが同じ番号を持つことはない**
——飛ぶことだけが違いで、それは見た目の問題である。

### アーカイブは削除ではない

`archivedAt` は `deletedAt` と別の列。
**アーカイブされたプロジェクトはダッシュボードとヘッダーの切り替えから消え、
永久に読める。削除されたものは30日で完全に消える**（[ADR 0015](./0015-soft-delete-items-hard-delete-accounts.md)）。
AsanaもBacklogも同じ場所に線を引いている。

APIは `archived: boolean` を取り、行には**いつ**を書く。
人が答えられる質問をAPIが訊き、事実の記録はサーバが持つ。

### 値域はまたトリガー

色・キーの文字種・期間の前後関係を、CHECKではなくトリガーで守る。

`projects` は `todos` / `shares` / `project_members` / `labels` から参照されていて、
SQLiteは外部キーを行ごとに検査する。**CHECKを足すにはテーブルを作り直すしかなく、
作り直せば最初の子行で失敗する**（[ADR 0011](./0011-expand-contract-migrations.md)）。
`user.role` が migration 0019 で選んだのと同じ取引である。

列の追加は6つのALTERだけで済む（すべて NULL 可か既定値付き）。
`key` の既定値 `''` は、**SQLiteが行のあるテーブルにNOT NULL列を既定値なしで足せない**
という理由だけで存在する。既存の行にはmigrationが `P{id}` を入れ、以降はAPIが必ず要求する。

### 作成もダイアログにする

入力欄1つのフォームをダイアログに置き換えた。
[ADR 0030](./0030-put-adding-and-sharing-behind-buttons.md)がタスク追加に対して出したのと同じ理由:
**名前しか訊かない画面は、他の項目が存在しないと教えている**。

## Consequences

### 得たもの

- タスクが `ALC-12` として、口頭でもチャットでも指せるようになった。
- 終わったプロジェクトを、消さずに片付けられるようになった。
- 一覧・切り替え・カードで、プロジェクトが色と説明で見分けられる。

### 残っている穴

- **タスク番号がプロジェクト内連番ではない**（上記）。
- **リード / 既定の担当者が無い。** Jiraにはある。
- **アバター画像が無い。** 色だけ。
- **キーを変える手段が無い。** 打ち間違えたら作り直すことになる。
- **アーカイブしても書き込みは止まらない。** 一覧から消えるだけで、タスクは編集できる。

### テストで気付いたこと

E2Eのアカウントが全員 "E2E user" という名前だった。担当者を選ぶテストが
**2人の同姓同名から「最後の一致」を選んでいた**ので、外したい相手ではなく
オーナーに割り当てていた。名前を渡せるようにした。

プロジェクトキーはインスタンス内で一意で、E2Eのデータベースは1回の実行で共有される。
名前から自動生成すると、"Board" を作るテストが2つあるだけで衝突する——
そして2つ目は**キーとは無関係に見える場所で落ちる**。ヘルパーが毎回一意なキーを打つようにした。
