# 0024. Todoの完了状態を真偽値から`status`に置き換え、詳細情報を持たせる

## Status

Accepted

## Context

Todoが持っていたのは `completed: boolean` だけで、
**「着手した」「詰まっている」を表現する手段が無かった**。
加えて `dueAt` と `priority` はスキーマにあるのに**画面から設定する手段が無く**、
シードでしか値が入らない状態だった。作った側だけが存在を知っている列である。

真偽値のまま「進行中フラグ」「ブロック中フラグ」を足す案は却下した。
**1行が同時に複数を主張できてしまう**ためで、それは表現力ではなく不整合の余地である。

## Decision

**`completed` を捨て、`status`（`todo` / `in_progress` / `blocked` / `done`）にする。**
あわせて `startAt`・`description` を足し、すべてを1つのダイアログから設定できるようにする。

`blocked` は**終端状態ではない**。作業が止まった理由であって、終わり方ではない。

### 移行はexpand/contractの2段階（[ADR 0011](./0011-expand-contract-migrations.md)）

0011（expand）で列を足してバックフィルし、`completed` も並行して書き続ける。
0012（contract）で `completed` を落とす。1段階でやると、
**コードとスキーマが食い違うデプロイの瞬間が、データを失う向きに生じる**。

drizzle-kitは「新しい列が古い列にとってどういう意味か」を知りようがないので、
**バックフィルは手で足した**。無いと完了済みのタスクが全部「未着手」に戻る。
行は全部残っているので、気づきにくい形で壊れる。

### 更新エンドポイントを1本に統合した

以前は完了状態（`PATCH /api/todos/:id`）とそれ以外（`/details`）で2本に分かれていた。
完了が真偽値で、他が「詳細」だったからである。
**完了が他と同じ1フィールドになった今、2本あることは所有スコープを書き忘れる場所が2つあること**でしかない。

`/details` にはクライアントの呼び出し元が1つも無かった。つまり期限も優先度も、
**APIとしては存在するのに設定できない**状態だった。これが目標の「設定可能にする」の本体である。

### 部分更新: 省略と `null` を区別する

省略は「変えない」、`null` は「空にする」。同じ扱いにすると
**「期限を外す」が表現できなくなる**。

これはテストが2回、実際のバグとして捕まえた:

1. `description` のzod `.transform()` が `undefined` を `null` に畳んでいた。
   **省略しただけの部分更新が、毎回メモを消していた。**
2. 作成ハンドラが `title` しか転送しておらず、日付付きで作ったTodoが日付を失っていた。

### CHECK制約をDBに置く

`status` の値域と `startAt <= dueAt` をCHECKで縛る。zodだけにしない理由は明確で、
**バリデーションは1リクエストしか見えない**——`startAt` だけを動かすPATCHは、
渡されていない `dueAt` と比較できない。**行全体を見ているのはDBだけ**である。

### 一覧の絞り込みは `status` と同じ語彙にしない

`all` と `active` は**statusではなく、statusを名指ししない方法**である。
`active` は「`done` 以外」で、これはどの単一statusでも表せない
（そして状態が増えても意味が変わらない）。同じクエリパラメータに並べておくことで、
「まだ残っているもの」と「ブロック中のもの」を1つの仕組みで聞ける。

型の上でも `TodoStatus`（行が持つもの）と `TodoFilter`（一覧を狭める方法）を分けてある。

## Consequences

### 実測で分かったこと —— 生成されたマイグレーションは「空なら通る」

`todos` は `attachments` から参照される親テーブルなので、
[ADR 0011](./0011-expand-contract-migrations.md)が言う通りdrizzle-kitの生成版はD1で失敗する……
**と思って実行したら、成功した。** 予測が外れたので測り直した:

| `attachments` の行数 | 生成版の結果 |
|---|---|
| 0行 | **成功する** |
| 1行 | `FOREIGN KEY constraint failed` |

外部キーは**テーブル単位ではなく行単位**で検査される。つまりこのマイグレーションは
**ローカル開発でもCIでも通り続け**（その時点で添付が無いのが普通）、
**実際に添付を持つ最初のデータベースで初めて落ちる**。
ADR 0011の `NOT NULL DEFAULT` の発見と同じ形で、同じ理由でたちが悪い。

手書きのdetach/reattachにしてある（`attachments` を先にFK無しで作り直す）。

### 実測で分かったこと —— 地雷は本当に埋まっていた

[ADR 0018](./0018-fts5-trigram-search.md)は「`todos` を作り直すとFTSのトリガー3本が
黙って消える」と書いていた。今回それが**初めて道の上に出た**。実際に消えた。

しかも `todos_fts` は行を保持したままなので、**検索は答え続ける**——
テーブルと一致しなくなった結果を返しながら、何もエラーを出さない。

**安全網が鳴ることも確かめた。** トリガー復元をわざと書かずにマイグレーションを適用し、
`test/worker/migrations.test.ts` が赤くなるのを見てから足した。
ADR 0018が「そのために置いた」テストが、本当にそのために働いた。

### 残っている穴

- ~~**FTSは `title` しか索引していない。**~~ migration 0013で `description` も索引に加えた。
  FTS5の列は作成時に固定されるので仮想テーブルごと作り直しているが、
  索引は`todos`から再構築できる派生データなので、捨てても失うものは時間だけである。
- **状態遷移に制約が無い。** `done` から `blocked` へ直接戻せる。
  ワークフローとして正しいかはドメインが決まっていないので縛っていない。
- **`startAt` を過ぎても何も起きない。** 「開始予定」であって、通知も強調も無い。
- **担当者がいない。** Projectは単一オーナー（[ADR 0014](./0014-user-owned-projects.md)）なので、
  割り当てる相手が存在しない。
- **CHECK制約は将来のrebuildで落ちうる。** ADR 0011がUNIQUE制約について書いたのと同じ性質で、
  drizzle-kitの生成するrebuildは制約を再発行しない。migrationsテストが存在を見ている。
