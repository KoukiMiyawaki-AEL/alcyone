# 権限とアクセス制御

誰が何を見られ、何を変えられるか。**このシステムで最も間違えやすく、
間違えても型エラーにもテスト失敗にもならない領域**なので、判定は少数の場所に集めてある。

## 3つのロール

ロールは強さの段階ではなく**役割**である。`user.role` に持ち、
`USER_ROLES = ["member", "admin", "owner"]` の**配列順が強さ**を表す。

| ロール | 何のためのアクターか | 見える | プロジェクトの設定を変えられる | プロジェクトを作れる |
|---|---|---|---|---|
| `owner` | システムの管理 | 全プロジェクト | 全プロジェクト | ○ |
| `admin` | **参加している**プロジェクトの設定管理 | 全プロジェクト | 自分が作ったもの＋参加しているもの | ○ |
| `member` | 参加したプロジェクトで作業する | 参加しているものだけ | 自分が作ったものだけ | × |

**見える範囲は広く、変えられる範囲は狭い。** 多くのシステムと逆向きで、意図的である。

- 管理者が全プロジェクトを見られるのは、**探せる必要があるから**。「あのプロジェクトの
  参加者を直して」と言われて辿り着けないなら、役割が成立しない。
- 管理者が参加していないプロジェクトの設定を変えられないのは、**ロールが入口ではないから**。
  誰かが参加者として追加する必要があり、その行が「誰が・いつ」を残す。
  ロールだけで入れると、何も残らない。

**`owner` はインスタンスのオーナーであって、プロジェクトの作成者ではない。**
後者は `projects.ownerId` で、別のスコープの別の概念である。画面では後者を
「プロジェクトの作成者」と呼び、語を分けている。

## 最初のアカウントがオーナーになる

`user` テーブルが空のときに作られたアカウントは `owner` になる
（`src/worker/auth.ts` の `databaseHooks.user.create.before`）。
権限を渡せるのは既に持っている人だけなので、**誰もいない状態から誰かを作る手段が要る**。

「最初」はフラグではなく**テーブルの件数**で判定する。フラグは消せば再発動できるが、
件数を戻すには全アカウントの削除が要り、それはもう別の状況である。

**`role` はBetter Authの `additionalFields` として宣言されている（`input: false` 付き）。**
宣言しないとBetter Authが知らないフィールドを落とすので、フックが返した値も保存されない。
`input: false` により、サインアップにも `update-user` にもこのフィールドを渡せない。
つまり**フックとサーバ内部からしか書けない**。

`user.role` の値域はトリガー（`user_role_known_insert` / `_update`）で守っている。
CHECK制約にできないのは、SQLiteが既存テーブルに制約を追加できず、`user` を作り直すと
`session` と `account` が `ON DELETE CASCADE` で消えるため。

## 2つのスコープ

サーバ側の判定は `src/worker/db/repo.ts` の2つの関数にしかない。
`createRepo(binding, ownerId, role)` が返すメソッドは**すべてスコープ済み**で、
ハンドラは絞り込まれていないクエリを受け取ることがない。

```
accessibleProjectIds()   作成者 or 参加者 or (admin | owner)     ← タスクを読み書きする
ownedProjectIds()        owner ? 全部 : (作成者 or (admin かつ 参加者))
                                                                 ← 削除・共有・参加者の変更
```

**タスクを触るのが前者、プロジェクトを消す・共有する・参加者を変えるのが後者。**
混ぜると参加者が鍵を配れるようになる。

`repo` に新しいメソッドを足すときは、必ずどちらかで絞ること。
この2つに集約してあるおかげで、ロールの意味を変えるときの編集も2箇所で済む。

## 参加者

プロジェクトは参加者を持つ（`project_members`）。参加していない人からは、
プロジェクトの存在ごと見えない（管理者以上を除く）。

- **作成者は参加者の行を持たない。** アクセスは `projects.ownerId` から来る。
  行も作ると**食い違いうる2つの事実**になる（行を消された作成者、持ち主が変わったのに残る行）。
  INSERTが明示的に拒む。
- **追加は `{ userId }` か `{ email }`。** 前者は名簿から選ぶ管理者向け、
  後者は宛先を知っている人向け。名簿（`GET /api/users`）は管理者以上しか読めない。
  アドレスでの追加は**アカウントの有無を1件ずつ問い合わせられる**ので、IP単位で絞っている。
  存在しないアドレスの答えは、管理できないプロジェクトの答えと同じ `404`。
- **除外はその人の担当も外す。** 1つのbatchで「履歴を書く → 担当を外す → 参加行を消す」。
  開けなくなった人の名前が担当欄に残ると、**誰もやっていないタスクが、誰かがやっているように
  表示される**。3つの文すべてに同じ権限チェックが載っているので、権限の無い呼び出しは
  どこにも書かない。

## プロジェクトを作れるのは管理者以上

どのプロジェクトが存在するかは運用の決めごとであって、作業の一部ではない。
誰でも作れると、**誰の承認も無く自分が管理者である場所を持てる**ので、
「参加には必ず誰かが行を作る」という原則がそこだけ破れる。

- **参加条件は付かない。** 作る時点で参加すべきプロジェクトが存在しない。
- **拒むのは `projects.create`**（ハンドラではない）。絞り込む行が無いので、
  `WHERE` ではなく「何も選ばない文」を返す。
- **作成者は降格しても、自分が作ったプロジェクトを管理し続ける。**
  「作れる資格」と「作ったものへの責任」は別の時点の話で、後者は資格の取り消しでは消えない。
  そうしないと、降格が**そのプロジェクトを一時的に誰も管理できない状態**にする。
- **件数の上限は無い。** 権限は「誰が」、上限は「どれだけ」で、別の恐れに答える仕組みである。

## 画面の可視性

サーバがデータを拒むこととは別に、**どの画面が誰に見えるか**を1箇所で決める
（`src/components/app/access-gate.tsx`）。

**保証は描画時に置く。** ルートの `beforeLoad` ガードでは足りない——
`beforeLoad` は遷移のときにしか走らず、**サインアウトは遷移ではない**。
描画時のゲートなら、要件を満たさない限り**保護コンポーネントもローダーも動かない**。

- 各ルートが `staticData: { access: "public" | "user" | "admin" }` を宣言する。
  **書き忘れは `user`**——公開しない側に倒れる。
- `access` は**最低ランク**で、オーナーは `admin` を満たす。集合にすると同じ順序を
  2箇所で表すことになり、`owner` を書き忘れた画面がオーナーに見えなくなる。
  **これは画面のスケールであって、上のプロジェクト単位のスコープとは別物。**
- **公開は `/login` と `/s/$token` の2つだけ。** この一覧は
  `test/components/access.test.ts` が全ルートを走査して固定する。表ではなくテストなのは、
  パスの表がルートの改名で静かにズレるため。
- URLも `/login` に合わせる（`replace: true`。保護URLを履歴に残さない）。
- **セッション未確定の間は全画面ローディング。外枠も出さない**——ヘッダーは
  アカウントメニューとプロジェクト切替を持ち、どちらもセッションを読むので、
  早く出すと空の切替と名前の無いボタンが出て直後に差し替わる。
- **公開ルートは待たない。** 「公開」はセッションを必要としないという意味であって、
  「セッションが無いことを確かめる」ではない。共有リンクは受け取った人にとって
  このアプリの最初の画面で、他人のセッション取得を待たせる理由が無い。
- **公開ルートは外枠の外に描く。** ヘッダーとサイドバーはサインインした人の家具で、
  共有ページの周りに置くと、リンクを開いただけの人に**その人のものではないアプリの目次**が出る。
- **権限不足はメッセージ。** URLはそのまま、ゲートが共通の「権限がありません」を描く。
  コンポーネントもローダーも動かない。追い出すと、古いリンクを踏んだ人に
  「壊れている」のか「権限が無い」のかが伝わらない。

### ローダーの401は別の信号

ゲートは「手元にセッションが無い」を扱い、ローダーの `401 → redirect` は
「手元のセッションが**もう無効**」を扱う。重複ではない。消すと、サーバ側で
セッションを失効させられた利用者が、エラーカードの並ぶ画面を触り続けることになる。

### セッションを終える出口は1つ

`src/features/auth/session-exit.ts` の `endSession()`。`signOut()` のあと
**ハードナビゲーション**（`window.location.assign`）で `/login` へ出る。

ルーターのローダーキャッシュ・Reactのstate・クロージャに捕まった配列——どれも
前のユーザーのデータを持ちうる。1つずつ消す設計は「消し漏れが無いこと」を
レビューで担保するが、**ページを捨てる設計は仕組みで担保する**。

**`redirect` パラメータは付けない。** サインアウトは意図した退出で、持ち越すと
次にサインインした人が前の人の画面に着地する。401だけが `redirect` を付ける。

**退会も同じ出口を通る。** 行が消えても、いま画面に描かれている状態は消えない。

## レート制限

`src/worker/rate-limit.ts` の `enforce()` を通す。認証系はIP単位、認証済みの重い処理は
ユーザー単位。**location単位かつ結果整合で、Cloudflare自身が「正確な計上には使うな」と
明記している**——濫用のコストを上げるものであって、割当量ではない。

`get-session` も `/api/auth/*` の一部なので数に入る。**429は「サインインしていない」と
見分けが付かない**ので、そう見える不具合を追うときは最初にここを疑うこと。
