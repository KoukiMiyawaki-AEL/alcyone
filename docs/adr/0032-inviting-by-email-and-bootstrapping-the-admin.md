# 0032. メールアドレスで招待し、最初のアカウントを管理者にする（0031の残った穴を塞ぐ）

## Status

Accepted（[ADR 0031](./0031-project-membership-and-roles.md)が「残っている穴」として
挙げた3点のうち2点を塞ぐ）

## Context

[ADR 0031](./0031-project-membership-and-roles.md)は参加者と管理者ロールを入れたが、
自分で書いた「残っている穴」のうち、**次の2つは穴ではなく欠落**だった。

- **所有者は誰も招待できない。** 追加は `{ userId }` しか取らず、その id の出どころは
  `GET /api/users`——管理者専用の名簿だけだった。所有者が設定画面を開くと、
  空のセレクトボックスと「一覧は管理者だけが取得できます」という注記が出る。
  **機能が画面にあって使えない**状態で、これは未実装より悪い。
- **管理者が存在しない。** 全アカウントが `member` で始まり、ロールを変える口はAPIに無い。
  つまり新しくデプロイしたインスタンスには管理者がひとりもおらず、名簿も参加制御も
  誰にも届かない。「DBを直接触るしかない」と書いたが、**データベースコンソールが要る機能は
  製品の機能ではない**。

3つめ（サイドバーにプロジェクトを選ぶ場所が無い）も同じ性質だった。
0031は「サイドバーがプロジェクト内の移動を担う」と書いたが、**そのプロジェクトを選ぶ手段は
一覧ページにしか無く**、サイドバーは「特定のプロジェクトを選択した状態を前提」と
言いながら前提を満たす方法を持っていなかった。

## Decision

### 追加は `{ userId }` か `{ email }` のどちらか

`POST /api/projects/:projectId/members` のボディを union にした。
optional な2フィールドにしなかったのは、**「両方」と「どちらも無い」を解釈する責任**が
ハンドラに生まれるため。union なら zod が入口で落とす。

`{ email }` も 0031 と同じ insert-from-select で、`user` をメールアドレスで join し、
`ownedProjectIds(projectId)` で絞る。**権限が文の一部**という性質は変わらない。

```sql
insert into project_members ("projectId", "userId", "addedBy", "createdAt")
select projects.id, user.id, ?, ?
  from projects, user
 where projects.id in (<ownedProjectIds>)
   and user.email = ?
   and projects.ownerId <> user.id
returning id
```

**存在しないアドレスの答えは `404`** ——管理できないプロジェクトの答えと同じにしてある。
書き分けると、プロジェクトの権限が無い相手にアカウントの有無を教えることになる。

**IP単位のレート制限を通す。** アドレスを受け取る以上、1件ずつ試せば
「このサービスに誰が登録しているか」を列挙できる。上限は濫用のコストを上げるだけで
割当量ではない（[ADR 0024](./0024-rate-limiting.md)と同じ性質）。

### 最初に作られたアカウントが管理者になる

Better Auth の `databaseHooks.user.create.before` で、`user` が空なら `admin` を入れる。

検討して捨てた案:

- **ロールを付与するエンドポイント** —— 到達できる誰もが呼べるエンドポイントになる。
  「最初の1回だけ」を状態で守ろうとすると、その状態を消せば何度でも通る。
- **手順書のSQL** —— 0031が実質これで、上に書いたとおり製品の機能ではない。
- **環境変数で管理者のアドレスを指定** —— デプロイ前にそのアドレスの持ち主が
  サインアップしているとは限らず、「まだ存在しないユーザー」を待つ分岐が増える。

「最初」はフラグではなく**テーブルの件数**で判定する。フラグだと消せば再発動できるが、
件数なら再発動には全アカウントの削除が要り、それはもう別の状況である。

**この値は `additionalFields` として宣言しないと保存されない。** Better Auth は
知らないフィールドを落とすので、フックが返した `role` も落ちていた（テストが赤くなって
気付いた。宣言前は全員 `member` のままだった）。宣言と同時に `input: false` を付けてあり、
これがもう半分——サインアップにも `update-user` にも `role` を渡せない。
**宣言することでフックが書けるようになり、`input: false` でリクエストからは書けないままになる。**

### 権限の変更は1文で、最後の管理者は降ろせない

`PATCH /api/users/:userId/role`。管理者のみ。

```
where id = ? and (<昇格である> or <対象が管理者でない> or <管理者が2人以上>)
```

判定と更新を2文に分けると、**最後の2人が同時に互いを降格できる隙間**ができる。
条件を WHERE に置けば、更新される行が0件になるだけで済む。

「対象が管理者でない」の項が要る理由は、これが無いと**管理者が1人のときに一般ユーザーを
一般ユーザーにする**（何も変わらない操作）まで拒まれるため。守りたいのは人数であって
操作の回数ではない。

### サイドバーがプロジェクトの切り替えを持つ

一覧・ボード・タイムラインの上に、参加しているプロジェクトを並べる。

**ルートのloaderではなくフックで取る。** サイドバーはルートではない。
そして購読元は `useAuth()` であって router context ではない ——
context はナビゲーション時にしか再解決されないので、
**ハードリロードでは何かをクリックするまで一覧が空のまま**になる
（[ADR 0017](./0017-realtime-with-durable-objects.md)で一度踏んだのと同じ穴）。

`router.subscribe("onResolved")` で再取得する。`router.invalidate()` は必ず resolve で
終わるので、プロジェクトを作った/消したページからこの一覧も更新される。

プロジェクト間のリンクは **search params を引き継がない**。絞り込みは離れる側の
プロジェクトのものであって、持ち込むと移った先で黙って行が消える。
表示の切り替え（一覧/ボード/タイムライン）は逆に引き継ぐ——同じプロジェクトの中だから。

## Consequences

### 得たもの

- 所有者が、名簿を見ずに、知っているアドレスで人を呼べる。
- 新しいインスタンスに管理者が最初から存在する。運用手順にDBコンソールが要らない。
- 管理者が画面から権限を渡せる（`/admin`）。
- サイドバーが「プロジェクトを選ぶ→表示を選ぶ」を1か所で担う。

### 残っている穴

- **招待は既存アカウント宛だけ。** 未登録のアドレスは `404` で、サインアップへの
  招待メールは送れない（メール基盤が無い——[ADR 0013](./0013-better-auth.md)）。
- **参加者に段階が無い。** 閲覧のみ、といった中間の権限は依然として無い。
- **プロジェクトの譲渡ができない。** 0031から変わっていない。
- **管理者の操作に監査ログが無い。** タスクの編集履歴はあるが、
  「誰が誰を管理者にしたか」はどこにも残らない。
- **`/admin` のガードはUIの都合。** 実際に拒んでいるのはサーバで、
  `beforeLoad` のリダイレクトは白い画面を見せないためだけのもの。

### テストで気付いたこと

`resetAll()` が**管理者を1件シードするようになった**。しないと、各テストが最初に
サインアップしたユーザーが自動的に管理者になり、**所有スコープのテストが
全権限を持ったユーザーで通ってしまう**（何も証明していないのに緑になる）。
ブートストラップ自体を検証するテストだけ `resetAll({ seedAdmin: false })` を使う。
