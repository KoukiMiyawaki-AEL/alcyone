# 0021. リクエストごとにD1 Sessionを開き、bookmarkをCookieで引き継ぐ

## Status

Accepted

## Context

D1は読み取りをレプリカに逃がせる。レプリカはプライマリより**遅れている**。
何もしないと、ごく普通の操作列で壊れる:

1. ユーザーがProjectを作る（プライマリに書かれる）
2. 一覧を読む（追いついていないレプリカに当たる）
3. **さっき作ったProjectが無い**
4. リロードすると出てくる

これは「たまに起きる不具合」に見えるが、実際には**一貫性モデルどおりの挙動**である。
つまりバグ報告としては再現しないし、コードを読んでも原因が書かれていない。
[ADR 0004](./0004-router-loader-over-query.md)でmutation後に `router.invalidate()` で
即座に再取得する方針を採っているので、**この経路は毎回踏む**。

D1 Sessions APIは、セッション内の全クエリが**アンカーしたbookmark以降の状態**を見ることを保証する
（sequential consistency）。bookmarkをリクエスト間で運べば、保証が1リクエストを超えて延びる。

## Decision

**`/*` の最初のミドルウェアでセッションを開き、bookmarkをHttpOnly Cookieで往復させる。**

実装前に3点を実測した（推測で決めない）:

| 確かめたこと | 結果 |
|---|---|
| drizzleは `D1DatabaseSession` を受け取れるか | **受け取れる**（drizzleが使うのは `prepare` と `batch` だけで、両方ある） |
| ローカルのminiflareはbookmarkを返すか | **返す**（`00000000-0000000c-...`） |
| そのbookmarkで次のセッションをアンカーできるか | **できる** |

### 認証も同じセッションに載せる

`createAuth(env, db)` にセッションを渡す。**サインインはセッション行を書き、
直後のリクエストがそれを読む**——read-your-own-writesの教科書的なケースがまさにここにある。
アプリのクエリだけ守って認証を守らないと、「ログインしたのにログインしていないことになる」
という最悪の形で出る。

そのためミドルウェアは `requestId()` の直後、**認証ルートより前**に置く。
下流の読み手が全員ひとつの順序を共有する必要がある。

### Cookieは `set` ではなく `append`

認証エンドポイントは**同じレスポンスに**自前のCookieを載せる。
`set` すると**サインインした瞬間にサインアウトさせる**ことになる。
テストで固定してある。

### サブリクエスト由来のレスポンスはヘッダが不変

これは実装中に踏んで、**realtimeのテスト8本が一斉に落ちて**気づいた。

`/api/realtime` はDurable Objectの `fetch` が返したレスポンスをそのまま返す。
**サブリクエストから返ったレスポンスのヘッダは不変**で、`append` すると
`Can't modify immutable headers` を投げる。`onError` が拾って500になるので、
**エンドポイントが単に壊れる**。

対処は、失敗したらレスポンスを組み直すこと。ただし **101だけは組み直せない**
（WebSocketは新しいResponseへ持ち越せない）ので、そのレスポンスはbookmark無しで出す。
ソケット自体はクエリを持たないし、次の通常リクエストで設定されるので実害は無い。

回帰テストを置いてある。**「全リクエストに何かを足す」ミドルウェアは、
自分で作っていないレスポンスに出会う**という一般則の実例。

### 壊れたbookmarkはエラーにしない

Cookieはユーザーに見えない。古い・壊れた値で**リクエストを失敗させるのは筋が通らない**ので、
`first-unconstrained` に落ちる。失うのは順序の保証だけで、それは元々無かったものである。
[ADR 0018](./0018-fts5-trigram-search.md)の検索カーソルと同じ扱い——
**位置であって命令ではない**。

### bookmarkが無いときは `first-unconstrained`

`first-primary` ではない。**一貫すべき相手がまだ無い**のに、
誰も要求していない保証のためにプライマリまでの遅延を払う理由がない。

### cronはセッションを使わない

`createRepo` は `D1Database` と `D1DatabaseSession` の両方を受ける。
スケジュール実行には**writesを一貫させるべきユーザーがいない**ので、素のDBを渡す。

## Consequences

### 得たもの

- レプリカ遅延に由来する「作ったのに出てこない」が構造的に起きなくなる。
- D1 Sessions API（`withSession` / `getBookmark` / bookmarkのアンカー）が実際に入った。
- 認証とアプリのクエリが同じ順序を共有する。

### 検証できていないこと —— ここが弱い

**ローカルにレプリカが存在しない。** miniflareのD1は1つで、遅れる相手がいない。
つまり**この機能が防ぐはずの症状を、一度も再現できていない**。
テストが押さえているのは配線（bookmarkが出る・往復する・壊れても落ちない・
認証Cookieを潰さない）であって、**一貫性モデルそのものではない**。

これは[ADR 0003](./0003-d1-local-only.md)（D1はローカルのみ）の制約が
そのまま効いている領域で、実アカウントで読み取りレプリケーションを有効にするまで
本当の検証はできない。**「入れたから安心」と読まないこと。**

### その他の穴

- **Cookieが増える。** bookmarkは短いが、全リクエストに載る。
- **タブをまたぐと共有される。** Cookieなので複数タブが1つのbookmarkを上書きし合う。
  bookmarkは「これ以降」の意味なので古い方に上書きされても正しさは壊れないが、
  最適ではない。
- **`Max-Age` は1日**。根拠は「使われていないbookmarkを運び続ける意味がない」で、
  測って決めた値ではない。
- **WebSocketは対象外。** アップグレード応答にCookieは載るが、
  その後のメッセージにセッションの概念は無い。
