# 実サービス化に必要なもののマップ

Status: Living（随時更新。更新のきっかけは「ADRを1本追加したとき」と「トリガーが実際に発火したとき」の2つ）

## Summary

alcyoneを実際に公開・運営するサービスにするなら何が必要になるかの**索引**。各項目に「なぜ必要か」と「いつ必要になるか（トリガー）」だけを持たせ、深掘りはしない。

**これはバックログでも約束でもない。** 優先順位も期日も持たない。役割は、後から「これを考えていなかった」で手戻りするのを防ぐことだけ。

## Background & Problem

alcyoneは[技術検証の台](../adr/0010-alcyone-as-proving-ground.md)であり、Todoリストはこのスタック（React + TanStack Router + Hono + Drizzle + Cloudflare D1）を動かすための題材に過ぎない。ターゲットユーザーがB2BかB2Cかは**まだ決めていない**。

この状態で困るのは「機能が足りないこと」ではない。足りないのは当たり前で、それは分かっている。**本当に困るのは、何にいつ着手すべきかの判断材料が無いこと**である。判断材料が無いと2種類の失敗が起きる。

1. まだ要らないものを作る（認証もユーザーもいないのに権限モデルを設計する）
2. **後から直すと高くつくものを、安いうちに手当てし損ねる**（オーナー列、時刻の表現、IDの形）

2つ目が本題。この文書は「[一方通行のドア](#p1-一方通行のドア)」を先頭に置き、その後ろに網羅的なカタログを置く。

### この文書の形について

[`docs/design/README.md`](./README.md)は design doc の分量を「1時間程度で書ける」目安としており、この文書はそれを超える。カタログ型なので構造上避けられない。

ただし1時間ルールが本当に守ろうとしていたのは**保守の編集コストが低いこと**だと解釈し、そちらを守る。1行の追加・削除が5分以内で終わる形（ほぼ全部が表、howは書かない、代替案は書かない）にしてある。

また[`template.md`](./template.md)は「Xを作る」前提のフォーマットで、カタログとは噛み合わない。セクション名はハウスフォーマットとして残し、適応は Proposal の内部構造で吸収している。

## Goals & Non-Goals

**Goals**

- 実サービスに必要な要素を、抜けが出ない粒度で一覧化する
- 各項目に「なぜ必要か」と「いつ必要になるか」を持たせる
- 後戻りが高くつく決定を前面に出す
- この文書をADRの発生源にする（マップ → 決定 → ADR という流れ）

**Non-Goals**

- 実装しない
- 優先順位付きバックログではない。期日を持たない
- 各項目を深掘りしない（深掘りはADRか個別のdesign doc）
- ターゲットユーザー（B2B / B2C）をここで決めない
- ライブラリを選定しない（選定はADR）

## Proposal

### P0. 読み方

**バケツの割り当てルール**: 「誰が困るか」ではなく**「実際に手を動かす場所」**でバケツを決める。1行は1バケツにだけ置く。相互参照は最大1つ、行の複製はしない。

**トリガーの種別**（各行に1つ）:

| 種別 | 意味 |
|---|---|
| 前提 | Xより前に済んでいなければならない |
| 閾値 | 数えられるものが線を越えたら |
| 要求 | 外部から求められたら |

トリガーは**観測可能な事象**で書く。「必要になったら」は循環していて、この種の文書がウィッシュリストに腐る経路そのものなので使わない。数えられるものは今の値を添える（現在: APIハンドラ9本 / テーブル6個 / 画面4枚）。

**状態の語彙**（この4つだけ）: `未着手` / `検討中` / `済` / `見送り`

**この文書を生かし続ける2つの規則**

1. 済んだ行は取り消し線ではなく**削除し、1行のリンクに置き換える**。この文書の価値は未了の集合にあり、増える一方のマップは誰も開かない。表が縮むのは健全な兆候。
2. トリガーが発火したのに動かなかったら、**その理由を状態列に書く**。それが生きた文書と無視された文書の差。

### P1. 一方通行のドア

今なら安く、後からだと高い決定。**この文書の主役はここ。** 以降のカタログを読まなくても、ここだけで元は取れる。

すべての起点になる現行スキーマ（[`src/worker/db/schema.ts`](../../src/worker/db/schema.ts)）:

```ts
export const todosTable = sqliteTable("todos", {
  id: int().primaryKey({ autoIncrement: true }),
  title: text().notNull(),
  completed: int({ mode: "boolean" }).notNull().default(false),
  createdAt: text().notNull(),
  updatedAt: text().notNull(),
  projectId: int().notNull().references(() => projectsTable.id),
}, (t) => [index("todos_project_id_idx").on(t.projectId)]);
```

オーナー列なし、論理削除なし。

#### D1.〈解決済み〉オーナー / テナント列

`projects.ownerId` を入れ、`createRepo(binding, ownerId)` が返すメソッドを**すべて最初から
スコープ済み**にした（[ADR 0014](../adr/0014-user-owned-projects.md)）。ハンドラは絞り込まれていない
クエリを受け取らないので、忘れることが構造的にできない。

このドアが実害に変わる瞬間も確認済み: 平置きの `PATCH`/`DELETE /api/todos/:id` はtodoのidだけで
引いていたため、認証を入れた時点で他人のtodoを連番idで書き換えられる状態だった。回帰テストは
`test/worker/projects.test.ts` の `cross-user isolation`、**サブクエリを戻すと実際に落ちることを
確認してある**。

#### D2.〈解決済み〉`createdAt` の表現

ISO-8601 + `Z` に統一し、DBデフォルトをやめてアプリ生成にした。`updatedAt` も追加。既存行は
[ADR 0011](../adr/0011-expand-contract-migrations.md)のcontractマイグレーションで変換済み
（瞬時は保たれている）。テーブルから両方のデフォルトが消えていることを
`test/worker/migrations.test.ts` が固定している。

#### D3. 整数連番PKをURLに露出している

- **現状**: `/api/todos/:id` が `z.coerce.number().int().positive()`。ローカルDBの実データは**1行しかないのに `id` は `9`** で、autoincrementが作成総数を漏らしている実例になっている。
- **後で直すコスト**: 列挙可能なので認証を入れた瞬間にIDORの攻撃面になる。件数が漏れる（B2Bなら顧客に利用量を測られる）。クライアント生成IDが使えないので、[ADR 0004](../adr/0004-router-loader-over-query.md)のトリガーが発火して楽観的更新を入れるときに詰まる。環境をまたぐデータ移行で衝突する。UUIDへの全面移行を後からやると、全FK・全URL・ブックマーク・キャッシュ済みリンクが巻き添えになる。
- **今できる最小の一手**: 全面移行しない。内部の int PK は維持したまま、**外部公開用のIDを別列で持つ**（`crypto.randomUUID()` はWorkersで使える）。

#### D4. 削除ポリシーが無い

- **現状**: `DELETE` は物理削除。
- **後で直すコスト**: **失うのはコードではなくデータ**で、これは取り返せない。ゴミ箱・復元・誤操作からの回復が後から不可能になる。保持義務や削除請求に応える方法も無くなる。将来コメント等の関連テーブルができると参照整合の問題にもなる。
- **今できる最小の一手**: 実装は後でよいので、**ポリシーだけ今決める**（物理削除のままいく、と決めるのも立派な決定。決めていない状態が問題）。

#### D5. 監査証跡が無い（しかも素直に書くと動かない）

- **現状**: 誰が何をしたかの記録が一切無い。
- **後で直すコスト**: **遡って作れない。** B2Bのセキュリティレビューで最初に聞かれる項目でもある。さらにこのスタック固有の罠がある: 「todoを1件insert + 監査行を1件insert」を `db.transaction()` で囲むと**型は通るが実行時に落ちる**。D1に対話的トランザクションが無く、`BEGIN` が `cannot start a transaction within a transaction` で失敗するため。原子性の手段は `db.batch()` だけ。
- **今できる最小の一手**: 書き込みを1つの経路に集約し、**`batch()` に載せられる形にしておく**。今なら無料で、後からだと全ハンドラに波及する。

#### D6. APIのバージョニング / 互換ポリシーが無い

- **現状**: パスは `/api/projects/…` と `/api/todos/:id`、認証は `/api/auth/*`。バージョンは付いていない。契約は `hc<AppType>` によるコンパイル時結合（[ADR 0005](../adr/0005-defer-openapi.md)）。
- **後で直すコスト**: コンパイル時結合はクライアントとWorkerが同一成果物である限り有効。**だがその前提は既に部分的に崩れている**: SPAのバンドルはブラウザにキャッシュされるので、デプロイ直後は古いバンドルが新しいWorkerを叩く。**デプロイはクライアントから見て既に非アトミック。** 後から `/api/v1` を切ると、移行期間中は両方をホストすることになる。
- **今できる最小の一手**: 方針を決めて書くだけ（URLプレフィックス / ヘッダ / 加算的変更のみ）。**最初の本番デプロイより前に。**

#### D7.〈較正用〉エラーの機械可読コードが無い — これはドアではない

- **現状**: [`src/worker/validator.ts`](../../src/worker/validator.ts)が `{ error, issues }` に固定している。`code` フィールドは無い。
- **なぜドアではないか**: エンベロープが拡張可能なので、`code` の追加は加算的で安い。**ドアなのはフィールドではなく規律のほう** —— クライアントが `error` の**文字列**にマッチし始めた瞬間に高くつく。現状 [`src/lib/mutate.ts`](../../src/lib/mutate.ts)は `res.ok` と 401 しか見ていないので綺麗な状態。
- **今できる最小の一手**: 「`error` の文字列に依存しない」を規約として書くだけ。

（**すべてが一方通行ではない**ことの例としてここに置いている。他に安いもの: `compatibility_date` の更新、`env.staging` の追加、oxlint / oxfmt の入れ替え。）

#### D8. 一覧が全件返り、並び順が `id` 固定

- **現状**: `GET /api/projects/:projectId/todos` はそのProjectの全件を返す。`orderBy(todosTable.id)`。**レスポンスは `{ project, todos }` のエンベロープ**なので、カーソルを足すのは加算的で済む（裸の配列だった頃の破壊的変更は回避済み）。Project一覧 `GET /api/projects` は依然として裸の配列で全件返す。
- **後で直すコスト**: 裸の配列を返している側（Project一覧）は、カーソルを足すと全呼び出し元に対して破壊的。**D1では行儀の問題では済まない**: 課金される `rows_read` は**スキャンした行数**であり、かつ**1つのD1は単一スレッドでクエリを1件ずつ処理する**（スループット ≒ 1/平均クエリ時間）。インデックスの無い全件走査がそのまま課金と遅延の上限になる。並び順を `id` に固定したことは「挿入順」を製品仕様として焼き付けており、手動並び替えを足すには `position` が要る（既存行への後付けは推測になる）。
- **今できる最小の一手**: ページネーションの方式（カーソル / オフセット）と安定ソートキーを決める。実装は後でよい。

#### D9. D1の作成時オプションが不可逆

- **現状**: `database_id` はまだプレースホルダ（[ADR 0003](../adr/0003-d1-local-only.md)）。**実DBを1つも作っていない。**
- **後で直すコスト**: `wrangler d1 create` には**作成時にしか指定できない**オプションが2つある。
  - `--location`（`apac` / `wnam` / `weur` …）: プライマリの配置。書き込みは常にここへ行く。
  - `--jurisdiction`（`eu` / `us` / `fedramp`）: データの保管・処理を特定法域に制限する。**指定するとlocation hintは無視される。**

  `--jurisdiction` は技術ではなく**法務の決定**で、しかもDBを作る前にしか行えない。加えて1DBは最大10GB（引き上げ不可）で、Cloudflare自身が**テナントごとにDBを作る設計を公式に推奨**しているため、「全テナントで1つのD1」か「テナントごとにD1」かもここで分岐する。バックアップの粒度も連動する（後述 3-8）。
- **今できる最小の一手**: **この項目だけ「まだ決めない」に期限がある。** 期限は `wrangler d1 create` を叩く日。その前に決める。

#### D10.〈解決済み〉マイグレーション方針

expand/contract を採用した（[ADR 0011](../adr/0011-expand-contract-migrations.md)）。実データを入れた
ローカルD1で予行演習済み。**D1固有の制約が4つ見つかっており**（NOT NULL + REFERENCES を同時に
足せない、親テーブルを作り直せない、`PRAGMA foreign_keys` が無視される、`BEGIN` を書けない）、
いずれもADRに記録してある。

**残っている穴**: `test/apply-migrations.ts` は空のDBに適用するので、**CIはbackfillとデータ変換を
一度も実行していない**。データを動かすマイグレーションは毎回ローカルで予行演習すること。

#### D11. ログに載せてよい情報の範囲が決まっていない

- **現状**: `onError` が stack / method / path を出す。request ID も user ID も無い。
- **後で直すコスト**: **PIIが一度Workers Logsに入ると、保持期間内は消せない。** 保持は Paid で7日 / Free で3日。逆に request ID が無いことで、障害時にログを1リクエスト単位で束ねられない。
- **今できる最小の一手**: 「リクエストボディはログに出さない」を規約として書き、request ID を足す。今なら無料。

#### D12. 認証方式によっては `run_worker_first` の変更を伴う

- **現状**: `run_worker_first: ["/api/*"]`。[`initial-architecture.md`](./initial-architecture.md)がこれを「この構成の要」と書いている。
- **後で直すコスト**: この設定の帰結として、**HTMLシェル自体はゲートできない**（Workerがその前に立っていない）。Cookie / Bearer でAPIを守る形はそのまま互換で、SPAとしては普通。一方、シェルごとゲートする形（Cloudflare Access、サーバサイドでログインへリダイレクト）は設定変更を伴い、SPAフォールバックの挙動を導出し直すことになる。
- **今できる最小の一手**: なし（認証方式を決めるときに、どちらの形かを意識すればよい）。**知っておくことが手当て。**

### P2. ターゲットユーザーが未定なせいで宙に浮いている決定

B2BとB2Cで**答えが変わる**もの。ここが決まらないと下流が決められない。

| 決定 | B2Bなら | B2Cなら | 期限 |
|---|---|---|---|
| テナント境界 | 組織が第一級。ユーザーは組織に属する | ユーザーが第一級。共有は後付け | D1と同時 |
| D1の作成単位 | テナントごとにDBが現実的（分離要求・復元粒度） | 共有DB + 行レベル分離 | `wrangler d1 create` |
| `--jurisdiction` | 顧客の所在地で決まる。EU顧客を取るなら `eu` | 自社の判断で決められる | `wrangler d1 create` |
| 認証 | SSO / SAML / SCIM が調達要件になりうる | ソーシャルログイン + パスワードレス | 認証着手時 |
| 権限モデル | ロール・招待・権限委譲が要る | 実質不要（本人のみ） | 2人目のユーザー前 |
| 監査ログ | 必須。輸出機能まで求められる | 内部調査用で足りる | D5と同時 |
| 課金 | 席数課金・請求書・年契約 | 従量 or サブスク・カード決済 | 課金着手時 |
| SLA / サポート | 契約に書く。窓口と応答時間が要る | ベストエフォート | 有償化時 |
| アクセシビリティ適合 | 調達で適合水準を聞かれる（VPAT等） | 内部品質として扱える | 要求時 |

**この表自体が「まだ決めない」ことの費用計算書**になっている。期限列が `wrangler d1 create` の3行は、実DBを作る日までに決着が要る。

### P3. 能力マップ

#### 3-1. プロダクト & ドメインモデル

無いと、そもそも作るものが決まらない。

| 項目 | なぜ必要か | トリガー | 種別 | 状態 |
|---|---|---|---|---|
| 何のサービスかの定義 | Todoが何の代理表現なのかが決まらないと機能の是非を判断できない | 実ユーザーの1人目を招く前に | 前提 | 未着手 |
| 期限・優先度・担当 | タスク管理が「一覧」で終わるか「運用できる」かの境目 | ドメインを決めたとき | 前提 | 未着手 |
| 説明・添付・コメント | 業務利用では1行のタイトルに収まらない | 同上 | 前提 | 未着手 |
| 並び替え・グルーピング | `id` 順固定は挿入順を仕様として焼き付けている（D8）。Projectによるグルーピングは実装済み | 画面が3枚を超えたら（現在3枚 — あと1枚で発火） | 閾値 | 未着手 |
| 検索・絞り込み | 件数が増えると一覧が機能しなくなる | 1テーブルが1,000行を超えたら | 閾値 | 未着手 |
| 一括操作・キーボード操作 | CLAUDE.mdが掲げる「長時間の業務利用」は密度と打鍵数で決まる | ドメインを決めたとき | 前提 | 未着手 |
| 履歴・アクティビティ表示 | 「誰がいつ変えたか」はD5の監査ログとは別で、ユーザー向け機能 | D5に着手したとき | 前提 | 未着手 |

#### 3-2. アイデンティティ & テナンシー

無いと、2人目のユーザーが来た瞬間に破綻する。

| 項目 | なぜ必要か | トリガー | 種別 | 状態 |
|---|---|---|---|---|
| 認証方式の選定 | — | — | — | 済（[ADR 0013](../adr/0013-better-auth.md)） |
| パスワードを自前で持つか | — | — | — | 済（Better Authが純JS scrypt。ただし**Freeプランでは CPU 10ms に収まらない**） |
| セッション管理 | Better Authに委譲。Cookieの属性・失効・複数デバイスの扱いを自前で持っていないことは把握しておく | 期限を延ばす/短縮する要件が出たら | 要求 | 済（委譲） |
| テナントモデル | ユーザー所有で確定。組織単位は未着手（受け皿はBetter Authの organization プラグイン） | B2Bの1社目、または組織共有の要求 | 要求 | 済（[ADR 0014](../adr/0014-user-owned-projects.md)） |
| 権限・ロール | 2人目が来ると「見えてよい／編集してよい」が発生する | 1テナントに2人目が入るとき | 前提 | 未着手 |
| 招待フロー | 組織にメンバーを追加する手段。メール送信に依存する | ロールを入れたとき | 前提 | 未着手 |
| SSO / SAML / SCIM | B2B調達で要件になる。後付けはユーザーテーブルの作り直しになりやすい | 取引先から要件として提示されたら | 要求 | 未着手 |
| アカウント削除・退会 | 法務（3-7）と直結。削除ポリシー（D4）に依存する | 実ユーザーの1人目の前に | 前提 | 未着手 |

#### 3-3. データ & 整合性

無いと、壊れたデータが戻らない。

| 項目 | なぜ必要か | トリガー | 種別 | 状態 |
|---|---|---|---|---|
| オーナー / テナント列 | D1。忘れると型エラー無しで越境漏洩。**絞り込みを足す場所は`src/worker/db/repo.ts`の1箇所に集約済み**（列自体は未着手） | 実ユーザーの1人目がデータを入れる前に | 前提 | 未着手 |

### 発火したトリガーの記録

この文書の規約は「トリガーが発火したのに動かなかったら、その理由を状態列に書く」。**初めて実際に

**3-8「E2Eテスト」— 発火（画面が4枚になった）、未着手。**

理由: Playwright / Vitest Browser Mode は[ADR 0009](../adr/0009-component-tests-happy-dom.md)で見送っており、
CLAUDE.mdの「Not Yet」にも入っている。今回はその判断を覆さなかった。

**ただしこの見送りの根拠は、認証の作業で明確に弱くなった。** 実際に起きたこと:

- ログイン後に画面が遷移しない不具合（セッションフックとの競合）
- リダイレクトループ（2つのガードと命令的なnavigateが、1レンダー遅れるコンテキストを取り合った）

**3つとも、workerテストとcomponentテストのどちらにも掛からなかった。** 発見はすべてブラウザでの
手動確認による。認証によって「上から下まで繋がっているか」の検証価値が跳ね上がったことの、これ以上
明確な証拠は無い。

次にこの文書を見るとき、E2Eは最有力候補として扱うべきである。

## Alternatives

この文書の**形**として検討し、採用しなかったもの。個々の項目の代替案はここには書かない（それはADRの仕事）。

- **GitHub Issues / Projects で管理する**: 検索とアサインには向くが、**トリガーを持てない**。「いつ着手すべきか」がIssueの本文に埋もれ、棚卸しできない。未着手Issueが100件並ぶのはウィッシュリストであってマップではない。
- **項目ごとに `Proposed` のADRを立てる**: [`docs/adr/README.md`](../adr/README.md)は連番に欠番を作らない規約なので、決まっていないものをADR化すると**永遠にProposedのままの墓場**が索引を膨らませる。ADRは決めた後に書く。
- **サブシステムごとに小さなdesign docへ分割する**: 個々は読みやすくなるが、**バケツをまたぐ抜けが見えなくなる**。この文書の目的は網羅性なので、一覧性を優先した。分割は各項目に着手するとき（そのときは個別のdesign docを立てる）。
- **CLAUDE.mdの「Not Yet」だけで済ませる**: 現にそうしていたが、一覧に理由もトリガーも無く、**Cloudflare固有の制約が1つも書かれていなかった**。CLAUDE.mdは「今どう書くか」の文書であって、将来の判断材料を置く場所ではない。

## Definition of Success

完了率では測らない（完了しない文書なので）。測るのは**ヒット率**。

1. 新しくADRを書くとき、この文書のどの行に対応するかを必ず言える。言えなければマップに穴がある。
2. 「これを考えていなかった」で手戻りが起きたとき、その項目がこの表に無ければ**文書側の失敗**として即座に追記する。これがこの文書の唯一の性能指標。
3. 表の中に主観的なトリガーが混ざっていないこと。**表の行だけを対象にする**（この規則を説明している散文自体が引っかかると、恒久的に非0になって検査の意味が消えるため）:

   ```bash
   grep -nE '^\|.*(いつか|必要になったら|規模が大きくなったら|余裕ができたら)' docs/design/service-readiness-map.md
   ```

   これが**0件**であることが、トリガーが観測可能な事象で書かれていることの機械的な確認になる（[ADR 0003](../adr/0003-d1-local-only.md)のプレースホルダ確認と同じ手口）。
4. 実装・決定済みの行がリンクに置き換わり、**表が縮む方向にも動いている**。
