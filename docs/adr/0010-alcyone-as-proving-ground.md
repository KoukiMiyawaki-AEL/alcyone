# 0010. alcyoneを技術検証の台と位置づけ、プロダクト機能より基盤の完全性を優先する

## Status

Accepted

## Context

このリポジトリには、**何のためのサービスなのかがどこにも書かれていない。** README.mdもCLAUDE.mdも[`initial-architecture.md`](../design/initial-architecture.md)も、説明しているのはスタック構成だけで、ターゲットユーザーもドメインも記述が無い。ADR 0001〜0009も全て技術判断であり、製品の方向性に触れたものは1本も無い。

唯一の方向性の痕跡は、CLAUDE.mdの設計原則にある「業務利用でも長時間使用しやすいUIにする」という一文と、[ADR 0002](./0002-shadcn-base-ui-nova.md)が業務系UI向けの`nova`スタイルを選んでいることだけ。動いている機能は単一ユーザーのTodoリスト1本で、`todos`テーブルにはオーナー列すら無い。

この状態のまま「次に何を作るか」を考えると、判断の基準が無いために2種類の失敗が起きる。まだ要らないものを作ってしまうか、後から直すと高くつくものを安いうちに手当てし損ねるか、である。方向性を明文化しないまま個別の機能追加を始めると、この2つを見分ける手段が無い。

## Decision Drivers

- 「次に何を作るか」の判断に、毎回使える基準が要る
- ターゲットユーザー（B2B / B2C）を今決めるだけの材料が無い。決めないことを、無自覚な放置ではなく明示的な判断にしたい

## Decision

alcyoneを**技術検証の台（proving ground）**と位置づける。

- **Todoリストは題材であり、製品ではない。** 「Todoアプリとして良くする」ことは目的ではない。
- **プロダクト機能より、基盤・運営側の完全性を優先する。** このスタック（React + TanStack Router + Hono + Drizzle + Cloudflare Workers/D1）で実サービスを運営するなら何が必要になるかを洗い出し、検証することが目的。
- **ターゲットユーザー（B2B / B2C）は決めない。** ただし決めないことのコストは可視化する。どちらに転んでも困らない選択を優先し、**先に決めないと後で高くつくもの**は個別に識別して前倒しで判断する。

この判断に基づく網羅的な検討結果は[`docs/design/service-readiness-map.md`](../design/service-readiness-map.md)に置く。

## Alternatives considered

- **Todo管理を実プロダクトとして育てる**: 競合との差別化やプロダクトとしての優先順位付けが必要になる。既存のTodoサービスに対する優位性を持ち込む意図が無い以上、この方向で真面目に考えるのは投資として見合わない。
- **別の業務ドメインを載せることを前提に、Todoを捨てる**: ドメインが決まっていない段階でこれを選ぶと、単に何も進まない。Todoは「オーナー・期限・状態遷移・一覧」という共通構造を持っており、検証の題材として十分機能する。
- **位置づけを明文化しない（現状維持）**: 実際にこの状態だった。判断の基準が無く、CLAUDE.mdの「Not Yet」も理由とタイミングを持たない一覧に留まっていた。

## Consequences

- 「Todoアプリとして便利にする」提案は、それ自体では採用理由にならない。**このスタックで何を検証できるか**が判断基準になる。逆に、直接ユーザーの役に立たない基盤側の作業（認証、監査ログ、可観測性）が正当化される。
- ターゲットユーザーを決めないコストは消えるのではなく、繰り越される。[service-readiness-map](../design/service-readiness-map.md)のP2がその繰越残高であり、**`wrangler d1 create`を叩く日が一部の項目の期限**になる（作成時にしか指定できないオプションがあるため）。
- 実サービスとして公開する意思が生まれたら、このADRを新しいADRでSupersedeする。そのとき、この位置づけを前提に積み上げた判断（何を作らなかったか）を見直す必要がある。
- design docは書き換えてよい文書なので、[service-readiness-map](../design/service-readiness-map.md)が将来書き直されるとその形の理由が失われる。**この前提だけをADRとして固定する**のがこのADRの役割。

## Confirmation

`src/worker/db/schema.ts`のテーブルが`todos`1つのままで、かつ`docs/design/service-readiness-map.md`が存在することで、この位置づけが維持されていると確認できる。実プロダクト化に舵を切っていれば、ドメイン固有のテーブルが増え、このADRはSupersededになっているはず。
